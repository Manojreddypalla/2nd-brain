# 3.1.2 Byte Stuffing (Character Stuffing)

> [!info] Definition
> **Byte Stuffing** (also called **Character Stuffing**) is a framing technique in which **special bytes** are used to mark the **beginning and end** of a frame. If these special bytes appear inside the actual data, the sender inserts an **Escape (ESC)** byte before them so that the receiver does not mistake them for frame boundaries.

---

# Why Byte Stuffing?

Character Count had one major problem.

> [!warning]
> If the **Count Field** becomes corrupted, the receiver loses synchronization and every following frame may be interpreted incorrectly.

To solve this problem, instead of storing the frame length, we use **special characters** to indicate where a frame starts and ends.

---

# Basic Idea

Choose two special bytes.

Example

```
FLAG = F
ESC  = E
```

Frame Format

```
+--------------------------------+
| FLAG | Data | FLAG |
+--------------------------------+
```

Example

```
F HELLO F
```

The receiver knows

- First `F` → Start of Frame
- Last `F` → End of Frame

No counting is required.

---

# The Problem

Suppose the actual data is

```
HELLO F WORLD
```

Transmission becomes

```
F HELLO F WORLD F
```

Now the receiver sees

```
F → Start

HELLO

F → End ??
```

But that middle `F` was actually data.

The receiver gets confused.

---

# Solution: Escape Character (ESC)

Whenever the sender finds a **FLAG** inside the data,

it inserts an **ESC** character before it.

Example

Data

```
HELLO F WORLD
```

Sender transmits

```
F HELLO E F WORLD F
```

Now the receiver understands

```
E F

↓

This FLAG is DATA

Not End of Frame
```

---

# Sender Algorithm

Suppose

```
FLAG = F

ESC = E
```

For every byte

```
IF byte == FLAG

Insert ESC before FLAG

IF byte == ESC

Insert ESC before ESC

Else

Send normally
```

Finally

```
Add FLAG at beginning

Add FLAG at end
```

---

# Receiver Algorithm

Receiver reads bytes one by one.

If

```
FLAG
```

Frame starts or ends.

If

```
ESC
```

Ignore ESC.

Treat the next byte as ordinary data.

---

# Why Does It Work?

The receiver follows one simple rule.

```
FLAG

↓

Boundary
```

But

```
ESC FLAG

↓

Data
```

So

```
FLAG

≠ Always Boundary
```

Only an **unescaped FLAG** marks a frame boundary.

---

# Advantages

## 1. No Synchronization Problem

Unlike Character Count,

corruption of one byte does not permanently shift frame boundaries.

---

## 2. Easy to Understand

Simple sender and receiver logic.

---

## 3. Reliable

Widely used in character-oriented protocols.

---

## 4. Variable Length Frames

Frames can have any size.

---

# Disadvantages

## 1. Increased Frame Size

Extra ESC characters increase overhead.

---

## 2. Processing Overhead

Sender and receiver must check every byte.

---

## 3. Works on Byte-Oriented Links

Not suitable for bit-oriented protocols.

Bit-oriented protocols use **Bit Stuffing**.

---

# Applications

Used in

- PPP (older implementations)
- BISYNC
- Character-oriented communication protocols
- Serial communication

---

# Character Stuffing vs Character Count

| Feature | Character Count | Byte Stuffing |
|----------|-----------------|---------------|
| Boundary Detection | Count Field | FLAG Byte |
| Synchronization | Poor | Better |
| Stuffing Required | ❌ No | ✅ Yes |
| Count Corruption | Fatal | No Count Field |
| Used Today | Rare | Limited |

---

# Memory Trick

Imagine writing a story.

Normally,

```
.
```

means

```
Sentence Ends
```

But suppose you actually want to write

```
The symbol "." is important.
```

You put it inside quotes.

```
"The symbol . is important."
```

The quotation marks tell the reader

"This period is part of the text."

Similarly,

```
ESC FLAG
```

tells the receiver

"This FLAG belongs to the data."

---

# Summary

- Uses **FLAG** bytes to mark frame boundaries.
- Uses **ESC** byte to distinguish data from control information.
- Every FLAG inside data is preceded by ESC.
- Every ESC inside data is also escaped.
- Better than Character Count because synchronization is maintained.
