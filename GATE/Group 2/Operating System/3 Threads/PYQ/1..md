## Question

**Which of the following statements about threads is/are TRUE?**

---

# Option A

> **Threads can only be implemented in kernel space.**

❌ **False**

### Why?

Threads can be implemented in **two ways**:

1. **User-Level Threads (ULT)**
    
    - Managed entirely by a user-space thread library.
        
    - The kernel may not even know these threads exist.
        
2. **Kernel-Level Threads (KLT)**
    
    - Created and managed by the operating system kernel.
        

Since **both implementations exist**, saying **"only in kernel space"** is incorrect.

**Correct statement would be:**

> Threads can be implemented in **either user space or kernel space**, depending on the threading model.

---

# Option B

> **Each thread has its own file descriptor table for open files.**

❌ **False**

This tests whether you understand what belongs to a **process** and what belongs to a **thread**.

Recall:

A process owns resources like:

- Address Space
    
- Heap
    
- Code
    
- Open Files
    
- File Descriptor Table
    

Threads share these resources.

Example:

```
Process

├── Thread A
├── Thread B
└── Thread C

Shared:

✔ Code
✔ Heap
✔ Global Data
✔ File Descriptor Table
```

Suppose Thread A opens:

```c
FILE *fp = fopen("test.txt","r");
```

Can Thread B use it?

**Yes.**

Because the file descriptor belongs to the **process**, not to an individual thread.

If every thread had its own file descriptor table, sharing files between threads would become unnecessarily complicated, defeating one of the main advantages of threads.

So:

❌ Each thread has its own file descriptor table → False

✅ All threads share the process's file descriptor table.

---

# Option C

> **All the threads belonging to a process share a common stack.**

❌ **False**

This is one of the most common GATE traps.

Every thread executes its own function calls.

Suppose:

Thread A

```c
void A() {
    int x = 10;
}
```

Thread B

```c
void B() {
    int x = 20;
}
```

If both used the same stack:

```
Stack

x = 10

↓

x = 20

↓

Return Address
```

They would overwrite each other's:

- Local variables
    
- Function parameters
    
- Return addresses
    

The program would quickly crash or behave unpredictably.

Therefore:

Each thread gets its **own stack**.

Threads only share:

- Code
    
- Heap
    
- Global variables
    
- Open files
    

They **do not** share:

- Stack
    
- Registers
    
- Program Counter
    

---

# Option D

> **Threads belonging to a process are by default not protected from each other.**

✅ **True**

This is the most conceptual option.

Remember:

Threads share the same address space.

Suppose

```c
int balance = 1000;
```

Thread A can do

```c
balance = 500;
```

Thread B can also do

```c
balance = 0;
```

Nothing stops one thread from modifying memory used by another thread.

They all have equal access to the shared process memory.

Unlike processes, there is **no memory protection between threads of the same process**.

That's why bugs like:

- Race conditions
    
- Accidental overwrites
    
- Invalid pointer writes
    

can affect all threads.

If one thread corrupts shared memory, the others may crash too.

So:

✅ Threads are **not protected from each other by default.**

---

# Memory Table

|Shared by Threads|Private to Each Thread|
|---|---|
|Code|Stack|
|Heap|Registers|
|Global Variables|Program Counter|
|Open Files / File Descriptor Table|Thread State|
|Address Space|Thread ID|

---

## GATE Trick

Whenever you see a resource in a question, ask yourself:

> **"Is this a process resource or a thread resource?"**

- **Process resource** → Shared by all threads.
    
- **Thread execution state** → Private to each thread.
    

Using that rule:

- File Descriptor Table → Process resource → Shared → **B is false.**
    
- Stack → Execution state → Private → **C is false.**
    
- Memory protection → Threads share the same address space → **D is true.**
    
- User-Level Threads exist → **A is false.**
    

So the correct answer is **only D**.
