# Race Condition

---

# Definition

A **Race Condition** occurs when **two or more concurrent processes or threads access and modify shared data simultaneously**, and the **final result depends on the order (timing) of execution**.

> The outcome becomes **unpredictable** because it depends on which execution "wins the race."

---

# Why Does a Race Condition Occur?

A race condition requires **three conditions**:

1. Multiple execution units (processes/threads)
2. Shared resource (variable, file, memory, etc.)
3. At least one execution unit modifies the shared resource

If these conditions exist without proper synchronization, a race condition can occur.

---

# Example

Suppose:

```text
Balance = 1000
```

Two threads execute simultaneously.

### Thread A

```text
Balance = Balance + 100
```

### Thread B

```text
Balance = Balance - 200
```

Expected Result:

```
1000 + 100 - 200 = 900
```

---

# What Actually Happens?

Updating a variable is **not one CPU instruction**.

It consists of multiple steps.

### Thread A

```text
Read Balance

↓

1000

↓

Add 100

↓

1100

↓

Write Back
```

---

### Thread B

```text
Read Balance

↓

1000

↓

Subtract 200

↓

800

↓

Write Back
```

Suppose execution happens like this:

```text
Initial Balance = 1000

Thread A reads → 1000

Thread B reads → 1000

Thread A writes → 1100

Thread B writes → 800
```

Final Balance:

```text
800
```

Expected:

```text
900
```

One update is **lost**.

This is called a **Lost Update**, caused by a **Race Condition**.

---

# Why is it Called a "Race"?

Both threads are **racing** to access and update the shared variable.

Whichever thread writes last determines the final result.

Hence the name:

> **Race Condition**

---

# Real-Life Analogy

Imagine a shared whiteboard.

Current value:

```text
1000
```

Two students see it at the same time.

Student A writes:

```
1100
```

Student B, who still thinks the value is 1000, writes:

```
800
```

The final answer depends on **who writes last**.

---

# Where Do Race Conditions Occur?

- Shared Memory
- Global Variables
- Shared Files
- Databases
- Banking Systems
- Operating Systems
- Multi-threaded Applications

---

# Consequences

- Incorrect results
- Data corruption
- Lost updates
- Program crashes
- Inconsistent state
- Security vulnerabilities

---

# How Can We Prevent Race Conditions?

By ensuring that **only one execution unit accesses the critical code at a time**.

Common solutions:

- Mutex
- Semaphore
- Monitor
- Peterson Algorithm
- Atomic Instructions

These will be studied in the next topics.

---

# Characteristics

- Happens in concurrent systems.
- Requires shared data.
- Requires at least one write operation.
- Outcome depends on execution timing.
- Difficult to reproduce and debug.

---

# Race Condition vs Data Race

| Race Condition | Data Race |
|---------------|-----------|
| General logical error caused by concurrent access | Specific low-level unsynchronized memory access |
| May occur even without a formal data race | Usually refers to concurrent reads/writes without synchronization |
| Broader concept | Specific programming condition |

> **For GATE, you can usually treat "Race Condition" as the primary term.**

---

# GATE Points ⭐

- Occurs due to concurrent access to shared data.
- Final result depends on execution order.
- Requires:
  - Shared resource
  - Multiple execution units
  - At least one write operation
- Can lead to lost updates and inconsistent data.
- Prevented using synchronization mechanisms.

---

# Quick Revision ⭐

- Concurrent access.
- Shared resource.
- Timing-dependent result.
- Unpredictable outcome.
- Synchronization prevents race conditions.
