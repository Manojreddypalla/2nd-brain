# Mutex — GATE Notes

## What is Mutex?

**Mutex = Mutual Exclusion**

A Mutex is a synchronization mechanism used to make sure that **only ONE process/thread at a time enters a Critical Section**.

> 🧠 Think: **One lock → One owner → One process inside**

---

# Why Do We Need Mutex?

Suppose two threads modify the same variable:

```text
balance = 1000
```

Without protection:

```text
P1 ──→ balance
P2 ──→ balance
```

Both can access it simultaneously.

This can cause a:

> **Race Condition**

We need:

```text
P1 enters
     ↓
P2 must wait
     ↓
P1 finishes
     ↓
P2 enters
```

Mutex provides this behavior.

---

# Basic Idea

A Mutex has two important operations:

```text
lock()
unlock()
```

### `lock()`

Acquire the Mutex.

```text
lock(mutex)
     ↓
"I want exclusive access"
```

### `unlock()`

Release the Mutex.

```text
unlock(mutex)
      ↓
"Someone else can enter now"
```

---

# Basic Code

```c
lock(mutex);

// Critical Section

unlock(mutex);
```

Flow:

```text
lock()
  ↓
Critical Section
  ↓
unlock()
```

---

# Simple Example

Initially:

```text
Mutex = FREE
```

P1 executes:

```text
lock(mutex)
```

Now:

```text
Mutex = LOCKED

Owner = P1
```

P1 enters the Critical Section.

---

P2 arrives:

```text
P2 → lock(mutex)
```

But:

```text
Mutex = LOCKED
Owner = P1
```

Therefore:

```text
P2 → WAIT
```

---

P1 finishes:

```text
P1 → unlock(mutex)
```

Now:

```text
Mutex = FREE
```

P2 can acquire it.

```text
P2 → lock(mutex)
      ↓
Enter Critical Section
```

---

# Visual

```text
        MUTEX
          🔒

P1 → lock()
       ↓
   ┌───────────┐
   │ Critical  │
   │ Section   │
   └───────────┘
       ↓
    unlock()
       ↓
P2 → lock()
       ↓
   Critical Section
```

Only **one process/thread** enters at a time.

# Ownership ⭐⭐⭐

This is VERY important.

A Mutex has an **owner**.

Suppose:

```text
P1 → lock(mutex)
```

Then:

```text
Owner = P1
```

Normally P1 must release it:

```text
P1 → unlock(mutex)
```

So:

> **The thread that locks the Mutex should unlock it.**

---

# What Happens if Mutex is Already Locked?

Suppose:

```text
P1 owns Mutex
```

P2 tries:

```text
P2 → lock(mutex)
```

P2 has to wait.

There are two possible ways waiting can happen.

---

## 1. Busy Waiting

P2 continuously checks:

```text
Free?
 ↓
No

Free?
 ↓
No

Free?
 ↓
No
```

CPU is being used while waiting.

This is called:

> **Busy Waiting / Spinning**

---

## 2. Blocking

Instead of continuously checking:

```text
Mutex busy
    ↓
P2 goes to sleep
    ↓
CPU runs something else
    ↓
Mutex becomes free
    ↓
P2 wakes up
```

This avoids wasting CPU cycles.

---

# Important ⚠️

Do NOT memorize:

> Mutex = Busy Waiting

That's incorrect.

A Mutex implementation may **block** waiting threads.

A **Spinlock** specifically uses Busy Waiting.

---

# Mutex vs Spinlock

| Mutex | Spinlock |
|---|---|
| May block/sleep | Busy waits |
| Doesn't necessarily waste CPU while waiting | Uses CPU while waiting |
| Better for longer waits | Better for very short waits |
| Mutual Exclusion | Mutual Exclusion |

---

# Connection With Hardware Instructions

Earlier we studied:

- Test-and-Set
- Compare-and-Swap
- Swap

These are **low-level atomic hardware instructions**.

They can be used internally to implement locks.

Think in layers:

```text
CPU Hardware
     ↓
Atomic Instructions
     ↓
Test-and-Set / CAS / Swap
     ↓
Lock Implementation
     ↓
Mutex
     ↓
Protect Critical Section
```

So:

> Hardware instructions provide the **atomic mechanism**.

> Mutex provides the **easy synchronization interface**.

---

# Does Mutex Prevent Race Conditions?

✅ Yes, **if used correctly**.

Suppose every thread does:

```c
lock(mutex);

balance = balance - 100;

unlock(mutex);
```

Only one thread can modify `balance` at a time.

Therefore:

```text
No simultaneous access
        ↓
No Race Condition
```

---

# Can Mutex Cause Deadlock?

Yes.

Example:

```text
P1 owns Lock A
P1 wants Lock B

P2 owns Lock B
P2 wants Lock A
```

Now:

```text
P1 waits for P2
       ↑
       ↓
P2 waits for P1
```

Neither can continue.

> **Deadlock**

So Mutex provides Mutual Exclusion but does **NOT** guarantee deadlock freedom.

---

# Can Starvation Occur?

Yes, depending on the implementation/scheduling.

A process may wait for a very long time while other processes repeatedly acquire the Mutex.

---

# Advantages

- Prevents Race Conditions
- Provides Mutual Exclusion
- Simple `lock()` / `unlock()`
- Only one owner at a time
- Can use blocking instead of wasting CPU

---

# Disadvantages

- Deadlock possible
- Starvation possible
- Incorrect locking can cause problems
- Forgetting `unlock()` can leave others waiting

---

# Common GATE Traps

### Mutex always uses Busy Waiting.

❌ False

Mutex can block the waiting thread.

---

### Mutex has ownership.

✅ True

The thread that acquires it owns it.

---

### Mutex guarantees deadlock freedom.

❌ False

Multiple Mutexes can lead to deadlock.

---

### Multiple threads can own one Mutex simultaneously.

❌ False

Only **one owner at a time**.

---

### Mutex and Test-and-Set are the same thing.

❌ False

```text
Test-and-Set
     ↓
Low-level hardware primitive

Mutex
     ↓
Higher-level synchronization mechanism
```

# 🧠 Memory Trick

Think of **one bathroom with one key 🔑**.

```text
P1 takes key
     ↓
P1 enters bathroom
     ↓
P2 arrives
     ↓
P2 waits
     ↓
P1 leaves + returns key
     ↓
P2 takes key
     ↓
P2 enters
```

That is basically a Mutex.

> **Mutex = One Key + One Owner + One Process Inside**
