# Semaphore Implementation using wait() and signal() — GATE Notes

## Core Idea

A Semaphore uses two **atomic operations**:

```text
wait(S)
signal(S)
```

Also called:

| Operation | Other Names |
|---|---|
| `wait()` | `P()`, `down()` |
| `signal()` | `V()`, `up()` |

> 🧠 `wait()` = "I want permission."
>
> 🧠 `signal()` = "Permission/resource is available."

---

# 1. wait(S)

`wait()` is executed when a process wants to acquire a permit/resource.

Simple mental model:

```text
wait(S)
   ↓
Permit available?
   │
   ├── YES → Take it → Continue
   │
   └── NO  → Wait
```

---

## Simple Conceptual Version

```c
wait(S)
{
    while(S <= 0)
        ;               // Busy Waiting

    S--;
}
```

Meaning:

```text
Check S
   ↓
S > 0?
   │
   ├── YES → S-- → Continue
   │
   └── NO → Keep Waiting
```

> [!warning]
> The check and decrement must effectively be protected/atomic as part of the semaphore operation. Otherwise multiple processes could acquire the same permit.

---

# Example

Initially:

```text
S = 2
```

P1:

```text
wait(S)

2 → 1
```

P1 proceeds.

P2:

```text
wait(S)

1 → 0
```

P2 proceeds.

P3:

```text
wait(S)

S = 0
↓
No permit
↓
WAIT
```

---

# 2. signal(S)

`signal()` indicates that a permit/resource is being released or that an event has occurred.

Simple conceptual version:

```c
signal(S)
{
    S++;
}
```

Meaning:

```text
Return/produce permission
       ↓
A waiting process may proceed
```

---

# Example

Suppose:

```text
S = 0

P3 = Waiting
```

P1 executes:

```text
signal(S)
```

A permit becomes available.

```text
P3 can proceed
```

---

# Complete Flow

```text
             PROCESS
                │
                ▼
             wait(S)
                │
                ▼
       Permit Available?
          │           │
         YES          NO
          │           │
          ▼           ▼
    Acquire Permit   WAIT
          │
          ▼
      Do the Work
          │
          ▼
           signal(S)
          │
          ▼
 Release / Produce Permit
          │
          ▼
  Wake waiter if necessary
```

# Using Semaphore for Mutual Exclusion

Initialize:

```c
semaphore mutex = 1;
```

Each process:

```c
wait(mutex);

// Critical Section

signal(mutex);
```

---

## Dry Run

Initially:

```text
mutex = 1
```

P1 executes:

```text
wait(mutex)
```

Result:

```text
mutex = 0

P1 → Critical Section
```

P2 executes:

```text
wait(mutex)
```

But:

```text
No permit available
```

Therefore:

```text
P2 → WAIT
```

P1 finishes:

```text
signal(mutex)
```

Now P2 can proceed.

Therefore:

```text
Only one process
      ↓
Critical Section
      ↓
Mutual Exclusion
```

# Busy-Waiting Implementation

One possible conceptual implementation is:

```c
wait(S)
{
    while(S <= 0)
        ;

    S--;
}
```

If:

```text
S = 0
```

the process repeatedly executes:

```text
Check S
Check S
Check S
Check S
...
```

This is:

> **Busy Waiting**

CPU cycles are wasted while waiting.

---

# Blocking Implementation ⭐⭐⭐⭐⭐

Operating systems can instead block a process that cannot proceed.

A semaphore can conceptually maintain:

```text
Semaphore
│
├── value
│
└── waiting queue
```

---

## wait()

A common textbook-style model is:

```c
wait(S)
{
    S.value--;

    if(S.value < 0)
    {
        add this process to S.queue;
        block();
    }
}
```

---

## signal()

```c
signal(S)
{
    S.value++;

    if(S.value <= 0)
    {
        remove a process P from S.queue;
        wakeup(P);
    }
}
```

> [!important]
> Exact pseudocode conventions vary between textbooks. In this common convention, negative values are allowed and encode waiting processes.

---

# Understanding Negative Semaphore Values ⭐⭐⭐⭐⭐

This is important for GATE.

In the above convention:

```text
S < 0
```

does **not** mean:

> "Negative resources exist." ❌

Instead, the magnitude indicates waiting processes.

Example:

```text
S = -3
```

means:

```text
3 processes are waiting
```

So:

> `|S|` = Number of waiting processes, under this implementation convention.

---

# Dry Run with Negative Values

Suppose:

```text
S = 1
```

### P1 executes wait()

```text
S--

1 → 0
```

P1 proceeds.

---

### P2 executes wait()

```text
S--

0 → -1
```

Since:

```text
S < 0
```

P2 blocks.

Queue:

```text
[P2]
```

---

### P3 executes wait()

```text
-1 → -2
```

P3 blocks.

Queue:

```text
[P2, P3]
```

Now:

```text
S = -2
```

Meaning:

> Two processes are waiting.

---

# Now P1 Executes signal()

```text
S++

-2 → -1
```

Since:

```text
S <= 0
```

there is still a waiting process.

One process is awakened:

```text
P2 → READY
```

Queue becomes:

```text
[P3]
```

---

# Another signal()

```text
-1 → 0
```

Wake:

```text
P3
```

Queue becomes empty.

---

# Why wait() and signal() Must Be Atomic ⭐⭐⭐⭐⭐

Suppose:

```text
S = 1
```

P1 and P2 both execute `wait()`.

If operations weren't atomic:

```text
P1 reads S = 1

CPU switches

P2 reads S = 1
```

Both could believe a permit is available.

Result:

```text
P1 → enters
P2 → enters
```

❌ Race Condition.

Therefore:

> **wait() and signal() must execute atomically with respect to the semaphore state.**

Hardware primitives such as:

```text
Test-and-Set
CAS
```

can help implement this atomicity internally.

---

# Binary Semaphore Example

```text
S = 1
```

Use:

```c
wait(S);

// Critical Section

signal(S);
```

Only one process can proceed at a time.

---

# Counting Semaphore Example

Suppose:

```text
5 printers

S = 5
```

Each process:

```c
wait(S);

// Use Printer

signal(S);
```

Maximum:

```text
5 processes
```

can use printers simultaneously.

## ⭐ GATE Trap #1

❌ False

Under the common textbook model:

```text
wait → S--
signal → S++
```

---

## ⭐ GATE Trap #2

> `signal()` can wake a blocked process.

✅ True

If processes are waiting, `signal()` may wake one.

---

## ⭐ GATE Trap #3

> Semaphore value can never be negative.

❌ Not always.

In the common blocking implementation:

```text
S = -N
```

represents:

```text
N waiting processes
```

---

## ⭐ GATE Trap #4

> Negative semaphore means negative resources.

❌ False

It represents waiting processes under that convention.

---

## ⭐ GATE Trap #5

> `wait()` and `signal()` don't need to be atomic.

❌ False.

They **must be atomic**.

# Important Formula ⭐

For the common negative-value implementation:

```text
S >= 0
↓
Available permits/resources = S
```

```text
S < 0
↓
Waiting processes = |S|
```

# Quick Comparison

| Operation | Effect |
|---|---|
| `wait(S)` | Request/acquire |
| `signal(S)` | Release/signal |
| `wait()` successful | Process proceeds |
| `wait()` unavailable | Process waits/blocks |
| `signal()` with waiters | May wake one process |
