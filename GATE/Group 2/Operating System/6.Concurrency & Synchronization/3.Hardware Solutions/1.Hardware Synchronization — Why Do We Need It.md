# Hardware Synchronization — Why Do We Need It?

Before learning **Test-and-Set, Compare-and-Swap, or Swap**, first understand **why hardware synchronization exists at all**.

---

# The Problem: Shared Resources

Imagine two processes want to update the same bank account.

```text
Balance = 1000
```

### Process P1

Withdraw ₹100.

### Process P2

Withdraw ₹200.

Both execute at the same time.

---

Internally, each process performs:

```cpp
Read Balance
↓

Calculate New Balance
↓

Write Balance
```

These are **three separate CPU instructions**.

If the CPU switches between them, both processes may read the same old balance.

Example:

```text
Balance = 1000
```

### P1

```text
Reads 1000
```

CPU switches.

### P2

```text
Reads 1000

Writes 800
```

CPU switches back.

### P1

```text
Writes 900
```

Final balance:

```text
900
```

Correct answer should have been:

```text
700
```

This incorrect behavior is called a **Race Condition**.

---

# Why Does This Happen?

Because a CPU executes instructions one by one.

Your code:

```cpp
if(lock == 0)
    lock = 1;
```

looks like one statement, but the CPU actually performs something like:

```text
1. Read lock
2. Compare with 0
3. Store 1 into lock
```

The scheduler can interrupt after **any** of these steps.

So another process can sneak in before the lock is updated.

---

# The Critical Section Problem

A **Critical Section** is any part of code that accesses shared data.

Example:

```cpp
balance -= 100;
```

or

```cpp
counter++;
```

or

```cpp
queue.push(x);
```

Only **one process** should execute a critical section at a time.

This property is called **Mutual Exclusion**.

---

# Why Not Just Use Software?

Early operating systems tried solving this using only software.

Examples:

- Strict Alternation
    
- Peterson's Algorithm
    
- Dekker's Algorithm
    

These use ordinary variables like:

```cpp
flag[2]
turn
```

to coordinate processes.

---

## The Problem with Software Solutions

### 1. CPU Can Interrupt at Any Time

Even this:

```cpp
lock = 1;
```

is just a normal memory write.

Without special hardware support, the CPU can switch between operations, creating race conditions.

---

### 2. Limited Scalability

Peterson's Algorithm works only for **two processes**.

Modern systems have:

- 4 cores
    
- 8 cores
    
- 16 cores
    
- 64 cores
    

Software-only algorithms become impractical.

---

### 3. Performance

Software algorithms often involve repeatedly checking variables and coordinating turns.

Hardware provides a much faster, built-in mechanism.

---

### 4. Complexity

Software algorithms are difficult to design correctly and prove correct.

Hardware primitives are simpler building blocks.

---

# Why Hardware Synchronization?

The CPU provides **special instructions** that execute **atomically**.

**Atomic** means:

> The operation happens as **one indivisible step**.

No other process or thread can observe or interrupt it halfway through.

For example, instead of:

```text
Read
↓

Check
↓

Write
```

(which can be interrupted)

the CPU performs:

```text
Read + Modify + Write
```

as **one single atomic operation**.

---

# What Does Hardware Actually Provide?

The CPU exposes special instructions such as:

- **Test-and-Set (TSL)**
    
- **Compare-and-Swap (CAS)**
    
- **Swap (Exchange)**
    

These instructions guarantee that no two CPUs or threads can execute the same operation on the same memory location simultaneously.

---

# Software vs Hardware Synchronization

|Software Synchronization|Hardware Synchronization|
|---|---|
|Uses normal variables|Uses special CPU instructions|
|Can be interrupted between instructions|Executes atomically|
|Hard to scale|Works on multicore systems|
|Examples: Peterson, Dekker|Test-and-Set, CAS, Swap|

---

# Mental Model

Imagine a room with a key.

### Software approach

```text
Look at key
↓

Pick up key
```

Someone else could grab it between those two actions.

---

### Hardware approach

```text
Grab the key and check it
```

Both happen **at the exact same instant**.

Nobody can interrupt in between.

---

# GATE Points to Remember

- **Why hardware synchronization?**
    
    - To perform synchronization operations **atomically**.
        
- **What problem does it solve?**
    
    - Race conditions in the critical section.
        
- **Why not only software?**
    
    - Software instructions can be interrupted, don't scale well, and are harder to use correctly on modern multicore processors.
        
- **Examples of hardware primitives**
    
    - Test-and-Set
        
    - Compare-and-Swap (CAS)
        
    - Swap (Exchange)
        

---

## One important clarification

When people say **"software synchronization doesn't work"**, that's **not** correct.

Algorithms like **Peterson's Algorithm** are **correct** under their assumptions (for example, two processes and a suitable memory model). They are mainly valuable for **understanding synchronization** and proving concepts.

Modern operating systems, however, rely on **hardware synchronization instructions** because they are **fast, atomic, and practical on multicore processors**. Software algorithms are built on top of these hardware primitives rather than replacing them.
