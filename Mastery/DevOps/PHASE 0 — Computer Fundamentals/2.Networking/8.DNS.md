# DNS — Domain Name System

## What is DNS?

**DNS (Domain Name System)** translates human-readable domain names into IP addresses.

```text
google.com
    ↓ DNS
142.x.x.x
```

Machines communicate using IP addresses, while humans prefer names.

> DNS is basically the **naming system of the Internet**.

---

# Why DNS Exists

Without DNS, you would need to remember:

```text
142.250.x.x
```

instead of:

```text
google.com
```

DNS provides:

```text
Domain Name → IP Address
```

---

# How DNS Resolution Works

Suppose you open:

```text
example.com
```

Conceptually:

```text
Browser
   ↓
Local DNS Cache
   ↓
Recursive DNS Resolver
   ↓
Root DNS Server
   ↓
TLD Server (.com)
   ↓
Authoritative DNS Server
   ↓
IP Address
```

## Step 1 — Local Cache

Your system/browser first checks whether it already knows the answer.

```text
example.com → 93.184.x.x
```

If cached → use it immediately.

If not → ask a DNS resolver.

---

## Step 2 — Recursive Resolver

Usually provided by:

- ISP
    
- Organization
    
- Cloud/network environment
    
- Public DNS provider
    

The resolver does the lookup work for the client.

```text
Client → "What is example.com?"
```

---

## Step 3 — Root DNS Server

The resolver asks a Root server:

```text
Where is example.com?
```

Root doesn't normally return the final IP.

It says roughly:

```text
I don't know example.com,
but I know where .com is.
```

---

## Step 4 — TLD Server

**TLD = Top-Level Domain**

Examples:

```text
.com
.org
.net
.in
.io
```

The `.com` server points toward the authoritative nameservers for the domain.

---

## Step 5 — Authoritative DNS Server

This server contains the actual DNS records for the domain.

Example:

```text
example.com → 93.184.x.x
```

It returns the answer.

---

## Step 6 — Response + Cache

The resolver returns the IP to the client.

```text
example.com
     ↓
93.184.x.x
```

The answer is cached according to its **TTL**.

The application can now connect to that IP.

---

# Mental Model

Think of the lookup as delegation:

```text
Client
  ↓
Resolver
  ↓
Root
  │
  └── "Ask .com"
          ↓
        .com
          │
          └── "Ask example.com's DNS"
                       ↓
                Authoritative Server
                       │
                       └── IP Address
```

Important:

> Root and TLD servers usually **point you toward the next place to ask** rather than storing every website's IP.

---

# Recursive vs Iterative Query

## Recursive

Client asks the resolver:

```text
Give me the final answer.
```

```text
Client → Resolver → DNS hierarchy
Client ← Resolver ← Final IP
```

## Iterative

The resolver follows referrals:

```text
Root → Ask TLD
TLD  → Ask Authoritative
Authoritative → Final Answer
```

So:

> **Client asks recursively; resolver typically performs iterative lookups.**

# Important DNS Records

## A Record

Maps hostname → IPv4.

```text
example.com → 192.0.2.10
```

---

## AAAA Record

Maps hostname → IPv6.

```text
example.com → 2001:db8::10
```

---

## CNAME

**Canonical Name**

Creates an alias pointing to another hostname.

```text
www.example.com
        ↓
example.com
```

---

## MX

**Mail Exchange**

Specifies mail servers.

```text
example.com
    ↓
mail.example.com
```

---

## NS

**Name Server**

Specifies authoritative nameservers for a domain.

```text
example.com
    ↓
ns1.example-dns.com
```

---

## TXT

Stores text information.

Commonly used for:

- Domain verification
    
- SPF
    
- DKIM
    
- Security configuration
    

---

## PTR

Reverse DNS lookup.

Normal DNS:

```text
Domain → IP
```

PTR:

```text
IP → Domain
```

---

# TTL — Time To Live

DNS records are cached.

```text
TTL = 300 seconds
```

means the cached record can generally be reused for **5 minutes** before it should be refreshed.

This explains a classic DevOps situation:

```text
Old Server → 10.0.0.5

DNS changed

New Server → 10.0.0.10
```

Some users may temporarily still reach the old address because DNS caches haven't expired.

> DNS changes are not necessarily observed everywhere immediately because of caching.

---

# DNS Ports

DNS primarily uses:

```text
UDP 53
```

TCP port `53` is also used when required.

So remember:

```text
DNS → UDP/53 and TCP/53
```

# DevOps DNS Commands

## dig

Detailed DNS lookup:

```bash
dig example.com
```

Query a specific record:

```bash
dig example.com A
```

```bash
dig example.com MX
```

Query a specific resolver:

```bash
dig @8.8.8.8 example.com
```

---

## nslookup

Simple DNS lookup:

```bash
nslookup example.com
```

---

## host

Quick hostname lookup:

```bash
host example.com
```

# DNS Troubleshooting

If:

```bash
curl https://example.com
```

returns:

```text
Could not resolve host
```

Think:

```text
Application
    ↓
DNS configured?
    ↓
Resolver reachable?
    ↓
UDP/TCP 53 allowed?
    ↓
DNS record exists?
    ↓
Correct authoritative server?
    ↓
Cached stale record?
```

Useful first checks:

```bash
dig example.com
```

```bash
nslookup example.com
```

Then test a specific resolver:

```bash
dig @8.8.8.8 example.com
```

If direct IP connectivity works but hostname connectivity fails:

> Strong indication of a **DNS/name-resolution problem**.

# DNS in DevOps

DNS appears everywhere:

```text
User
 ↓
DNS
 ↓
Load Balancer
 ↓
Reverse Proxy
 ↓
Application
```

Also heavily used in:

- AWS / Azure / GCP
    
- Kubernetes
    
- Docker
    
- Service discovery
    
- Load balancing
    
- CDNs
    
- Microservices
    

Example Kubernetes-style communication:

```text
frontend
   ↓
backend-service
   ↓ DNS
Service IP
   ↓
Backend Pods
```

Applications often communicate using **service names**, not hardcoded IP addresses.

# Quick Revision

```text
DNS = Name → IP
```

Resolution:

```text
Client
 ↓
Resolver
 ↓
Root
 ↓
TLD
 ↓
Authoritative DNS
 ↓
IP Address
```

Important records:

```text
A      → IPv4
AAAA   → IPv6
CNAME  → Alias
MX     → Mail Server
NS     → Name Server
TXT    → Text/Verification
PTR    → IP → Name
```

Ports:

```text
UDP 53
TCP 53
```

Core DevOps idea:

> **DNS doesn't connect you to the server. DNS tells you which IP address you should connect to.**

After DNS resolution, protocols such as TCP/UDP take over communication.
