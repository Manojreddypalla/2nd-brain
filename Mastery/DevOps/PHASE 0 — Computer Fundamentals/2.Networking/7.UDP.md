# UDP — User Datagram Protocol

## What is UDP?

**UDP (User Datagram Protocol)** is a **connectionless transport-layer protocol**.

Unlike TCP, UDP does **not establish a connection before sending data**.

```text
TCP:

Connect → Send Data → Close


UDP:

Send Data →
Send Data →
Send Data →
```

> UDP prioritizes **speed and low overhead** over reliability.

---

# How UDP Works

UDP simply packages data into a **datagram** and sends it to the destination.

```text
Application
    ↓
UDP
    ↓
IP
    ↓
Network
```

Example:

```text
Client                         Server

  | ------ Datagram 1 --------> |
  | ------ Datagram 2 --------> |
  | ------ Datagram 3 --------> |
```

There is:

- No handshake
    
- No connection establishment
    
- No ACK
    
- No retransmission by UDP
    
- No connection termination
    

---

# UDP is Connectionless

TCP first performs:

```text
SYN → SYN-ACK → ACK
```

UDP does not.

It simply sends:

```text
Client -------- Data --------> Server
```

The sender doesn't inherently know whether the receiver received it.

---

# UDP Does NOT Guarantee

UDP does not guarantee:

- Packet delivery
    
- Packet ordering
    
- Duplicate protection
    
- Retransmission
    
- Flow control
    
- Congestion control
    

Example:

Sender:

```text
1 → 2 → 3 → 4
```

Receiver could theoretically receive:

```text
1 → 3 → 4
```

or:

```text
2 → 1 → 4 → 3
```

UDP itself does not repair this.

---

# Why Use UDP?

Because removing reliability mechanisms makes UDP **simple and low-overhead**.

Imagine a live video call.

If one packet is lost:

```text
Frame 100
Frame 101 ❌
Frame 102
Frame 103
```

Retransmitting Frame 101 later may be useless because the conversation has already moved on.

For many real-time applications:

> **Fresh data is more valuable than old recovered data.**

---

# UDP Header

UDP has a very small **8-byte header**.

```text
+---------------------+---------------------+
|    Source Port      | Destination Port    |
+---------------------+---------------------+
|       Length        |      Checksum       |
+---------------------+---------------------+
|                 Data                      |
+-------------------------------------------+
```

## Fields

### Source Port

Port number of the sending application.

### Destination Port

Port number of the receiving application.

### Length

Total size of:

```text
UDP Header + Data
```

### Checksum

Used for error detection.

> Checksum can detect corruption, but UDP does not itself retransmit corrupted/lost data.

---

# TCP vs UDP

|Feature|TCP|UDP|
|---|---|---|
|Connection|Connection-oriented|Connectionless|
|Handshake|Yes|No|
|Reliable delivery|Yes|No|
|Ordering|Yes|No|
|Retransmission|Yes|No|
|Flow control|Yes|No|
|Congestion control|Yes|No|
|Header|Minimum 20 bytes|8 bytes|
|Overhead|Higher|Lower|
|Communication model|Byte stream|Datagrams/messages|

# DNS Example

A client may send a DNS query:

```text
Client                      DNS Server

   | ---- DNS Query -------> |
   |                         |
   | <--- DNS Response ----- |
```

Traditional DNS queries commonly use:

```text
UDP Port 53
```

TCP is also used by DNS in various situations.

---

# DHCP Example

DHCP commonly uses UDP because a new machine may not yet have a configured IP address.

Ports:

```text
Server → UDP 67
Client → UDP 68
```

Typical process:

```text
DHCP Discover
      ↓
DHCP Offer
      ↓
DHCP Request
      ↓
DHCP ACK
```

Remember:

```text
DORA

Discover
Offer
Request
Acknowledge
```

# UDP and Ports

Just like TCP, UDP uses **port numbers** to identify applications.

Example:

```text
IP Address → identifies machine
Port       → identifies application
```

Example:

```text
192.168.1.10:53
```

means:

```text
IP   = 192.168.1.10
Port = 53
```

# UDP Troubleshooting

UDP can be trickier to troubleshoot because there is no TCP-style connection state.

TCP gives states like:

```text
SYN_SENT
ESTABLISHED
TIME_WAIT
CLOSE_WAIT
```

UDP does not maintain the same connection state machine.

So debugging often involves checking:

```text
Application
     ↓
Correct UDP Port?
     ↓
Firewall allows UDP?
     ↓
Routing correct?
     ↓
Packets reaching server?
     ↓
Application listening?
```

Useful tools:

```bash
ss -uan
```

```bash
tcpdump
```

```bash
nc
```

# Important DevOps Mistake

TCP and UDP ports are separate.

For example:

```text
TCP 53
```

and

```text
UDP 53
```

are not the same socket/protocol combination.

A firewall rule allowing:

```text
TCP/53
```

doesn't automatically mean:

```text
UDP/53
```

is allowed.

Always check the protocol when configuring:

- Firewalls
    
- Cloud Security Groups
    
- Kubernetes Services
    
- Docker ports
    
- Load Balancers

# Mental Model

Think of TCP like a **phone call**:

```text
Establish connection
      ↓
Communicate
      ↓
Confirm/recover data
      ↓
End connection
```

Think of UDP like **throwing messages toward someone**:

```text
Message →
Message →
Message →
```

No built-in confirmation that each one arrived.

# DevOps Interview Points

**What is UDP?**

A connectionless transport-layer protocol that sends independent datagrams without establishing a connection.

**Why is UDP generally lower-overhead than TCP?**

It does not provide TCP's handshake, retransmission, ordering, flow control, or connection state management.

**Does UDP guarantee delivery?**

No.

**Does UDP guarantee packet ordering?**

No.

**Does UDP use ports?**

Yes. UDP uses source and destination ports.

**Does UDP have error detection?**

Yes. UDP has a checksum, but UDP itself does not retransmit lost or corrupted datagrams.

**Why is UDP useful for real-time applications?**

Because in many real-time workloads, low latency and receiving current data can be more important than retransmitting old lost data.
