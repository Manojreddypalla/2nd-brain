## 1. What is Kubernetes?

**Kubernetes (K8s)** is an open-source platform used to manage **containerized applications**.

It helps automate:

```
Deployment
Scaling
Networking
Self-healing
Updates
Resource management
```

The basic mental model:

```
You describe WHAT you want
          ↓
      Kubernetes
          ↓
figures out HOW to maintain it
```

This is called **declarative configuration**.

---

# 2. Kubernetes Cluster

A Kubernetes system is called a **cluster**.

```
Kubernetes Cluster
│
├── Control Plane 🧠
│
└── Worker Nodes 💪
     ├── Pods
     ├── Pods
     └── Pods
```

The cluster contains:

**Control Plane** → manages the cluster.

**Worker Nodes** → actually run application workloads.

A cluster normally has one or more worker nodes.

---

# 3. Control Plane Components 🧠

The Control Plane maintains the overall state of the cluster.

### kube-apiserver

The **front door of Kubernetes**.

It exposes the Kubernetes HTTP API.

Conceptually:

```
kubectl
   ↓
API Server
   ↓
Kubernetes Cluster
```

Most requests to Kubernetes go through the API server.

---

### etcd

Kubernetes' **key-value data store**.

It stores the data representing the cluster's state.

Think:

```
etcd = Kubernetes' source of cluster state
```

For example, information about Kubernetes resources ultimately lives as API data backed by etcd.

---

### kube-scheduler

Decides **which Node should run a Pod**.

Example:

```
New Pod
   ↓
Scheduler

Node A → CPU busy ❌
Node B → enough resources ✅
Node C → memory low ❌

        ↓

Run Pod on Node B
```

More precisely, it finds Pods that haven't yet been assigned to nodes and selects suitable nodes for them.

---

### kube-controller-manager

Runs Kubernetes **controllers**.

Controllers continuously work toward the desired state.

```
Desired replicas = 3

Current replicas = 2

        ↓

Controller detects mismatch

        ↓

Create replacement
```

This is part of Kubernetes' **reconciliation** model.

---

### cloud-controller-manager

Optional component used when Kubernetes integrates with a cloud provider.

Think:

```
Kubernetes
    ↕
Cloud Controller
    ↕
Cloud infrastructure
```

It separates cloud-specific integration from the rest of the Kubernetes control plane.

---

# 4. Worker Node Components 💪

Worker Nodes are where your Pods actually run.

Important components include:

```
Worker Node
│
├── kubelet
├── container runtime
├── kube-proxy (optional)
│
└── Pods
     └── Containers
```

### kubelet

The **agent running on each Node**.

Its job is to ensure the Pods assigned to that node are running, including their containers.

Mental model:

```
Control Plane
     ↓
"Run this Pod"

kubelet
     ↓
makes sure the Pod is running
```

---

### Container Runtime

Software responsible for actually running containers.

Kubernetes itself isn't the low-level thing executing your application process.

Think:

```
Kubernetes
    ↓
Pod
    ↓
Container Runtime
    ↓
Container
    ↓
Application Process
```

---

### kube-proxy

An optional node component that maintains network rules used to implement Kubernetes **Services**.

For now remember:

```
kube-proxy
     ↓
Service networking
     ↓
traffic reaches Pods
```

We'll understand this much better when we study Kubernetes networking.

---

# 5. Kubernetes Objects

This is another **very important concept**.

Kubernetes represents the state of the cluster using **objects**.

Examples you'll encounter:

```
Pod
Deployment
Service
ConfigMap
Secret
Namespace
StatefulSet
DaemonSet
Job
```

An object is effectively a **record of your intent**.

You create an object describing what you want, and Kubernetes works to maintain that state.

---

# 6. Desired State

Suppose you create a Deployment saying:

```
I want 3 replicas.
```

That's your:

**Desired State**

Kubernetes might observe:

```
Desired = 3
Current = 2
```

Then:

```
Desired
   ↓
   3

Current
   ↓
   2

Mismatch
   ↓
Controller acts
   ↓
Create another instance
   ↓
Current = 3
```

This **desired state vs current state** idea is one of the foundations of Kubernetes.

---

# 7. `spec` vs `status`

Kubernetes objects commonly contain two important concepts:

```
spec   → what YOU want
status → what EXISTS now
```

Example:

```
spec:
    replicas: 3
```

means:

```
"I want three replicas."
```

Kubernetes maintains the object's status based on what is actually happening.

Conceptually:

```
SPEC
Desired State
     │
     ▼
 Kubernetes
     │
     ▼
STATUS
Current State
```

The control plane continually tries to make the actual state match the desired state.

---

# 8. Kubernetes Manifest

Objects are commonly described using **YAML manifests**.

Basic shape:

```
apiVersion: apps/v1
kind: Deployment

metadata:
  name: my-app

spec:
  replicas: 3
```

Four fields you'll see constantly:

```
apiVersion
kind
metadata
spec
```

### `apiVersion`

Which Kubernetes API version handles the resource.

### `kind`

What object you're creating.

Example:

```
kind: Pod
```

or

```
kind: Deployment
```

### `metadata`

Information identifying/describing the object.

Common example:

```
metadata:
  name: backend
```

### `spec`

The desired configuration/state of that object.

The exact contents of `spec` depend on the type of Kubernetes object.

# 9. kubectl

`kubectl` is Kubernetes' command-line tool.

Mental model:

```
YOU
 │
 │ kubectl
 ▼
Kubernetes API Server
 │
 ▼
Cluster
```

For example:

```
kubectl get pods
```

Conceptually means:

> Ask Kubernetes API for information about Pods.

And:

```
kubectl apply -f deployment.yaml
```

means:

> Send this desired configuration to Kubernetes.

`kubectl` makes Kubernetes API calls on your behalf.

---

# 10. Labels & Selectors

Kubernetes objects can have **labels**.

Labels are key/value metadata.

Example:

```
labels:
  app: backend
  environment: production
```

You can then select groups of objects using those labels.

```
Pods

Pod A → app=backend
Pod B → app=backend
Pod C → app=frontend

Selector:
app=backend

        ↓

Pod A
Pod B
```

This becomes extremely important for things such as Services and Deployments.

---

# 11. Namespaces

Namespaces logically divide resources inside a cluster.

Example:

```
Cluster
│
├── namespace: development
│     ├── Pods
│     └── Services
│
├── namespace: testing
│     ├── Pods
│     └── Services
│
└── namespace: production
      ├── Pods
      └── Services
```

Names generally need to be unique **within a namespace**, rather than across every namespace.

Namespaces become particularly useful with multiple teams/projects and resource isolation.

# 🧠 Kubernetes Mental Map

For now, keep this picture in your head:

```
                       YOU
                        │
                     kubectl
                        │
                        ▼
                 ┌─────────────┐
                 │ API SERVER  │
                 └──────┬──────┘
                        │
              CONTROL PLANE 🧠
          ┌─────────────┼─────────────┐
          │             │             │
        etcd        Scheduler    Controllers
     cluster state   placement    desired state
                                      │
                                      ▼
                           WORKER NODES 💪
                       ┌───────────────┐
                       │    kubelet    │
                       │       ↓       │
                       │     Pods      │
                       │       ↓       │
                       │  Containers   │
                       └───────────────┘
```

And the **one flow worth understanding instead of memorizing**:

```
You write YAML
      ↓
kubectl
      ↓
API Server
      ↓
Desired state stored/managed
      ↓
Controllers notice required work
      ↓
Scheduler chooses Node
      ↓
kubelet on Node
      ↓
Container runtime
      ↓
Pod / Container runs
```

That flow is basically the backbone we'll keep adding detail to.
