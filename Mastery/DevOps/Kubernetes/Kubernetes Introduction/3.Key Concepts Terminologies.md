Yep. Those are basically the **seven pillars of Kubernetes concepts**. I’d organize your master notes around exactly these headings.

## 1. Cluster Architecture

A Kubernetes **cluster** is a collection of machines working together to run containerized applications.

The architecture has two major sides:

```text
Kubernetes Cluster
│
├── Control Plane 🧠
│   ├── kube-apiserver
│   ├── etcd
│   ├── kube-scheduler
│   └── kube-controller-manager
│
└── Worker Nodes 💪
    ├── kubelet
    ├── container runtime
    ├── kube-proxy (optional)
    └── Pods
```

### Control Plane

The **Control Plane** manages the cluster.

Think:

> Control Plane decides; Nodes execute.

### kube-apiserver

The API server is the **front door of Kubernetes**.

When you execute:

```bash
kubectl get pods
```

the basic path is:

```text
kubectl
   ↓
kube-apiserver
   ↓
Kubernetes API
```

Components generally communicate with Kubernetes through its API.

### etcd

`etcd` is a distributed **key-value store** used as Kubernetes' backing store for cluster data.

Mental model:

```text
API Server
    │
    ▼
  etcd
    │
    └── cluster state
```

Losing the underlying cluster-state data without backups can be catastrophic, which is why etcd backup matters in cluster administration.

### Scheduler

The scheduler decides **which Node should run a newly created Pod**.

```text
Pod needs:
CPU = 2
RAM = 4GB

       ↓

Scheduler

Node A → insufficient RAM ❌
Node B → suitable ✅
Node C → unsuitable constraint ❌

       ↓

Node B
```

Scheduling can consider resources and placement constraints/preferences.

### Controller Manager

Runs controllers.

Controllers implement Kubernetes' reconciliation behavior:

```text
Desired replicas = 3
Current replicas = 2
        ↓
Controller detects mismatch
        ↓
work is triggered to restore 3
```

### Worker Node

A Node is a machine—physical or virtual—that runs workloads.

```text
Node
├── kubelet
├── container runtime
└── Pods
```

### kubelet

`kubelet` is the node agent.

It makes sure containers described by assigned Pod specifications are running and healthy as expected.

### Container Runtime

Actually executes containers.

Modern Kubernetes uses the **Container Runtime Interface (CRI)** to interact with compatible runtimes.

Common example:

```text
containerd
```

Mental chain:

```text
Kubernetes
    ↓
kubelet
    ↓
CRI
    ↓
container runtime
    ↓
container
```

### kube-proxy

`kube-proxy` is an optional networking component that helps implement Kubernetes Service networking on nodes.

Some networking implementations can provide equivalent functionality without kube-proxy.

### Architecture mental model

```text
                kubectl
                   │
                   ▼
             API SERVER
                   │
          ┌────────┼────────┐
          ▼        ▼        ▼
        etcd   Scheduler Controllers
                            │
                    CONTROL PLANE
                            │
              ──────────────┼────────────
                            │
                     WORKER NODES
                            │
                         kubelet
                            │
                           Pods
                            │
                       Containers
```

---

# 2. Containers

A **container** packages an application together with the dependencies needed to run it.

```text
Container
├── Application
├── Libraries
├── Runtime
└── Dependencies
```

Containers provide isolation while sharing the host kernel.

This is different from virtual machines.

```text
VMs

Hardware
   ↓
Host OS
   ↓
Hypervisor
   ↓
Guest OS
   ↓
Application
```

versus:

```text
Containers

Hardware
   ↓
Host OS / Kernel
   ↓
Container Runtime
   ↓
Containers
   ↓
Applications
```

That generally makes containers lighter than VMs.

### Container Images

A container normally starts from an **image**.

```text
Source Code
    ↓
Build
    ↓
Container Image
    ↓
Registry
    ↓
Pull
    ↓
Container
```

Images are packaged artifacts used to create containers.

For example:

```text
nginx:1.29
```

contains an image name and tag.

Kubernetes can pull images from registries and run them through the configured container runtime.

### Container Environment

Kubernetes provides containers with runtime information/configuration through mechanisms including environment variables, DNS, mounted configuration and storage.

Later we'll encounter:

```text
ConfigMaps
Secrets
Volumes
Services
```

### Container Lifecycle Hooks

Containers can receive lifecycle hooks such as:

```text
PostStart
PreStop
```

These allow applications to perform actions around lifecycle events.

### Runtime Classes

Kubernetes can support different container-runtime configurations through:

```text
RuntimeClass
```

Useful when workloads require different runtime properties.

---

# 3. Workloads

This is one of the **most important Kubernetes sections**.

A workload is an application or task running on Kubernetes.

The fundamental execution object is the:

# Pod

A **Pod is the smallest deployable compute object in Kubernetes.**

Usually:

```text
Pod
└── Container
```

but technically:

```text
Pod
├── Container A
└── Container B
```

is possible.

Containers inside the same Pod are tightly coupled.

They share resources including the Pod's network context and can share storage volumes.

Think:

```text
Pod
│
├── Shared network
├── Shared storage (when volumes configured)
│
├── App container
└── Helper container
```

### Why not manage containers directly?

Kubernetes manages **Pods**, giving it a unit around which networking, storage, scheduling and lifecycle can be coordinated.

```text
Kubernetes
    ↓
Pod
    ↓
Container(s)
```

---

## Pod Lifecycle

A Pod moves through lifecycle phases such as:

```text
Pending
   ↓
Running
   ↓
Succeeded / Failed
```

Pods aren't meant to be treated like immortal servers.

If one disappears, higher-level workload controllers can create replacements.

That's why Kubernetes workloads are generally built around:

> replace rather than lovingly repair one specific Pod.

---

# Controllers / Workload Resources

Usually you **don't manually create individual Pods** for production applications.

Instead:

```text
You
 ↓
Deployment
 ↓
ReplicaSet
 ↓
Pods
```

Higher-level workload resources manage Pods.

---

## Deployment

Used primarily for stateless application workloads.

Example:

```text
Deployment
replicas = 3

     ↓

┌─────┐ ┌─────┐ ┌─────┐
│ Pod │ │ Pod │ │ Pod │
└─────┘ └─────┘ └─────┘
```

Deployments provide functionality such as:

```text
Scaling
Rolling updates
Rollbacks
Declarative updates
```

If one managed Pod disappears, the controllers work to restore the required replica count.

---

## ReplicaSet

Maintains a specified number of Pod replicas.

```text
Desired = 3

Pod
Pod
Pod
```

If:

```text
Pod 💀
Pod ✅
Pod ✅
```

the system works toward:

```text
Pod ✅
Pod ✅
Pod ✅
```

Normally you interact with a **Deployment**, which manages ReplicaSets for you.

---

## StatefulSet

Used for workloads that require stable identity and/or stable storage characteristics.

Typical examples include some:

```text
Databases
Distributed systems
Stateful services
```

A conceptual difference:

```text
Deployment Pods

backend-x7g2
backend-4kd9
backend-92js

interchangeable
```

StatefulSet Pods have stable ordinal identities such as:

```text
database-0
database-1
database-2
```

---

## DaemonSet

Ensures a copy of a Pod runs on all or selected Nodes.

```text
Node 1 → monitoring-agent
Node 2 → monitoring-agent
Node 3 → monitoring-agent
Node 4 → monitoring-agent
```

Common uses:

```text
Logging agents
Monitoring agents
Networking components
Storage agents
```

Mental model:

> Deployment → "I want N copies."

> DaemonSet → "I want one on each applicable Node."

---

## Job

Runs work **to completion**.

```text
Start
 ↓
Perform task
 ↓
Finish
```

Examples:

```text
Data processing
Database migration
Report generation
Batch processing
```

---

## CronJob

Runs Jobs according to a schedule.

```text
CronJob
   ↓
Every day at 2 AM
   ↓
Job
   ↓
Pod
```

Think:

> Linux `cron`, but creating Kubernetes Jobs.

---

# 4. Services, Load Balancing & Networking

Now we encounter one of Kubernetes' trickiest but coolest areas.

Suppose:

```text
Deployment

Pod A → 10.1.1.5
Pod B → 10.1.1.8
Pod C → 10.1.2.4
```

Pods can disappear and replacements may have different IPs.

Your frontend shouldn't depend on:

```text
10.1.1.5
```

Therefore Kubernetes provides:

# Service

A **Service** exposes a network application running as one or more Pods behind a stable abstraction.

```text
             Service
                │
        ┌───────┼───────┐
        ▼       ▼       ▼
      Pod A   Pod B   Pod C
```

Services commonly identify backend Pods through labels/selectors.

Example mental model:

```text
Pod A → app=backend
Pod B → app=backend
Pod C → app=frontend

Service selector:

app=backend

        ↓

Pod A
Pod B
```

---

## Service Types

### ClusterIP

Default Service type.

Accessible within the cluster.

```text
Frontend Pod
     ↓
ClusterIP Service
     ↓
Backend Pods
```

---

### NodePort

Exposes the Service through a port on Nodes.

Conceptually:

```text
Outside
   ↓
NodeIP:NodePort
   ↓
Service
   ↓
Pods
```

---

### LoadBalancer

Requests/provisions external load-balancing functionality where supported by the environment.

```text
Internet
   ↓
External Load Balancer
   ↓
Service
   ↓
Pods
```

Common with cloud environments.

---

### ExternalName

Maps a Kubernetes Service to an external DNS name rather than selecting Pods.

---

# DNS

Kubernetes clusters normally provide internal DNS.

Instead of applications needing to know:

```text
10.96.83.42
```

they can resolve Service names.

Conceptually:

```text
frontend
   ↓
backend-service
   ↓
DNS
   ↓
Service
   ↓
backend Pods
```

---

# Ingress

Services expose applications, but you often need HTTP routing.

Example:

```text
example.com/api
        ↓
backend

example.com/shop
        ↓
shop-service
```

Ingress represents HTTP/HTTPS routing rules.

```text
Internet
   ↓
Ingress
   ↓
┌──────────────┐
│ /api → API   │
│ /web → Web   │
└──────────────┘
```

An **Ingress Controller** is needed to actually implement those rules.

Modern Kubernetes also has the broader **Gateway API**, which provides more expressive traffic-routing APIs.

---

# Network Policies

By default, depending on your networking implementation, Pods may have broad network reachability.

NetworkPolicy lets you express rules about which Pods may communicate.

Example:

```text
Frontend → Backend ✅

Backend → Database ✅

Frontend → Database ❌
```

Think:

> Firewall-like policy for Pod traffic.

Your network plugin must support NetworkPolicy enforcement.

---

# 5. Storage

Containers and Pods are disposable.

Data often isn't.

```text
Pod dies

Application process → gone
Pod filesystem → not something to rely on for persistent data

BUT

important database data must survive
```

Kubernetes therefore has storage abstractions.

---

## Volumes

Volumes provide storage accessible to containers in a Pod.

```text
Pod
├── Container
│      │
│      ▼
└── Volume
```

Volumes can have different lifetimes and backing implementations.

---

# PersistentVolume — PV

A **PersistentVolume** represents storage available to the cluster.

Mental model:

```text
PV
 ↓
Actual storage resource
```

For example, storage might ultimately come from:

```text
Cloud disk
Network storage
Storage system
```

---

# PersistentVolumeClaim — PVC

Applications shouldn't necessarily care about exactly which physical disk they receive.

Instead they request storage.

```text
Pod
 ↓
PVC
 ↓
PV
 ↓
Storage
```

Think:

```text
PV  = storage resource

PVC = request for storage
```

That's the key relationship.

---

# StorageClass

StorageClass describes classes of storage and can enable **dynamic provisioning**.

Without dynamic provisioning, administrators may need to create storage resources ahead of time.

With it:

```text
Developer creates PVC

"I need 20 GB"

       ↓

StorageClass

       ↓

Provisioner

       ↓

Storage dynamically created
```

So the chain becomes:

```text
Pod
 ↓
PVC
 ↓
StorageClass
 ↓
Provision storage
 ↓
PV
 ↓
Actual storage
```

---

# 6. Configuration

You don't want application images containing every environment-specific setting.

Bad mental architecture:

```text
backend-development:v1
backend-testing:v1
backend-production:v1
```

Better:

```text
Same application image
       +
Different configuration
```

Kubernetes gives us several mechanisms.

---

# ConfigMap

Stores **non-confidential configuration**.

Example:

```text
LOG_LEVEL=debug
API_URL=api.example.com
ENVIRONMENT=production
```

Then:

```text
ConfigMap
   ↓
Pod
   ↓
Application
```

Configuration can be exposed in different ways, such as environment variables or mounted files.

---

# Secret

Used for sensitive data.

Examples:

```text
Passwords
Tokens
Keys
Certificates
```

Conceptually:

```text
Secret
   ↓
Pod
   ↓
Application
```

Important security note:

**A Kubernetes Secret isn't automatically equivalent to "perfectly encrypted and secure."**

Base64 representation itself is **encoding, not encryption**. Cluster security configuration, RBAC, encryption at rest, external secret-management systems, etc. can matter in production.

---

# Environment Variables

Configuration can be supplied to containers through environment variables.

```text
Pod
 ↓
Container
 ↓

DATABASE_HOST=...
LOG_LEVEL=...
```

---

# Resource Management

Kubernetes also lets workloads describe CPU and memory requirements.

Two important concepts:

```text
requests
limits
```

### Request

The amount of resource Kubernetes uses when making scheduling decisions.

Example:

```text
CPU request = 500m
Memory request = 256Mi
```

Think:

> "I need approximately this much resource available for scheduling me."

### Limit

A maximum resource constraint for the container.

```text
CPU limit = 1 CPU
Memory limit = 512Mi
```

Simplified mental model:

```text
Request
   ↓
Scheduling / expected requirement

Limit
   ↓
Maximum allowed usage constraint
```

The exact runtime behavior differs between CPU and memory, something we'll study later.

---

# Probes

Kubernetes needs a way to understand application health.

Three probes matter a lot.

### Liveness Probe

Answers:

> Is this container still functioning?

If repeated liveness checks fail, Kubernetes can restart the container.

---

### Readiness Probe

Answers:

> Is this application ready to receive traffic?

```text
Pod running
   ↓
App still starting
   ↓
Readiness = false

Service should not send traffic yet.
```

Later:

```text
App ready
   ↓
Readiness = true
   ↓
Receive traffic
```

---

### Startup Probe

Answers:

> Has this application successfully started yet?

Useful for applications that require significant startup time.

Mental model:

```text
Startup
   ↓
Did you start?

Readiness
   ↓
Can you receive traffic?

Liveness
   ↓
Are you still healthy/alive?
```

---

# 7. Cluster Administration

Everything above is mostly:

> **How do I run applications on Kubernetes?**

Cluster Administration starts asking:

> **How do I operate Kubernetes itself?**

That includes areas such as:

```text
Creating clusters
Managing Nodes
Certificates
Authentication
Authorization
Networking
Upgrades
Backups
Resource management
High availability
Security
Logging
Monitoring
```

---

# Namespaces

Namespaces provide logical isolation/grouping inside a cluster.

```text
Cluster
│
├── development
│   ├── Pods
│   └── Services
│
├── testing
│
└── production
```

They're useful for separating:

```text
Teams
Projects
Environments
```

---

# RBAC

**Role-Based Access Control**

Controls who can perform which actions.

Example:

```text
Developer:

get Pods     ✅
create Pods  ✅
delete Node  ❌
```

Mental model:

```text
WHO
 ↓
can perform
 ↓
WHAT ACTION
 ↓
on
 ↓
WHICH RESOURCE
```

You'll encounter:

```text
Role
ClusterRole
RoleBinding
ClusterRoleBinding
```

---

# ResourceQuota

Prevents a namespace/team from consuming unlimited cluster resources.

Example:

```text
development namespace

CPU ≤ 20
Memory ≤ 40GB
Pods ≤ 100
```

---

# LimitRange

Can define/default resource constraints for objects such as containers within a namespace.

Think:

```text
ResourceQuota
     ↓
How much can the namespace consume overall?

LimitRange
     ↓
What constraints/defaults apply to individual workloads?
```

---

# Nodes

Administrators manage the machines participating in the cluster.

```text
Cluster
├── Node A
├── Node B
└── Node C
```

Nodes can be:

```text
Ready
NotReady
```

and can be controlled for scheduling.

---

# Cordon

Mark a Node as **unschedulable** for new Pods.

```text
kubectl cordon node1
```

Mental model:

```text
Node 1

existing workloads → remain

new workloads → ❌
```

---

# Drain

Safely evicts appropriate workloads from a Node so you can perform maintenance.

```text
Node 1
├── Pod A
├── Pod B
└── Pod C

       ↓ drain

workloads moved/recreated elsewhere as appropriate

       ↓

Node 1
maintenance
```

Typical workflow:

```text
cordon
  ↓
drain
  ↓
maintenance
  ↓
uncordon
```

---

# Taints & Tolerations

Used to influence which Pods can be scheduled onto certain Nodes.

Think of a **taint** as the Node saying:

> "Stay away unless you explicitly tolerate this."

```text
GPU Node
   ↓
TAINT

normal Pod ❌

GPU workload
+ toleration
     ↓
     ✅
```

This becomes useful for specialized machines.

---

# Affinity / Anti-Affinity

Allows more sophisticated placement preferences/rules.

### Affinity

> Put workloads together / put this workload on matching nodes.

### Anti-Affinity

> Keep workloads apart.

For example, three database replicas shouldn't necessarily all live on one physical Node:

```text
BAD

Node 1
├── DB1
├── DB2
└── DB3

Node 1 dies 💀
Everything gone.
```

Better:

```text
Node 1 → DB1
Node 2 → DB2
Node 3 → DB3
```

## The seven questions to remember

Instead of memorizing dozens of Kubernetes nouns, attach each section to a **question**:

|Area|Question it answers|
|---|---|
|**Cluster Architecture**|Who controls and executes everything?|
|**Containers**|What actually runs my application?|
|**Workloads**|How should my applications be managed?|
|**Networking**|How do applications find and communicate with each other?|
|**Storage**|Where does data live?|
|**Configuration**|How does my application receive settings, secrets and runtime requirements?|
|**Cluster Administration**|How do I securely operate the entire platform?|

And there's a dependency chain hiding here:

```text
Linux
 ↓
Containers
 ↓
Pods
 ↓
Workload Controllers
 ↓
Services / Networking
 ↓
Storage + Configuration
 ↓
Cluster Administration
```

That's the order I'd actually learn it in. **Don't jump into Helm, Operators, CRDs, service meshes, GitOps, etc. yet.** Once Pods → Deployments → Services → ConfigMaps/Secrets → Volumes make sense, those advanced tools have something solid to attach to.
