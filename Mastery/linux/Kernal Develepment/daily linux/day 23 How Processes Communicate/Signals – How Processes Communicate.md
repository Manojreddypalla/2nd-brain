# 🐧 Linux Internals – Day 23

## Signals – How Processes Communicate

> [!goal] Goal  
> Understand how Linux uses **signals** to asynchronously notify, control, pause, resume, and terminate processes.

---

# 1. What is a Signal?

A **signal** is an asynchronous notification delivered to a process indicating that some event occurred.

Signals can originate from:

- The **kernel**
    
- Another **process**
    
- The **terminal/user**
    
- The process itself
    

Examples:

```text
Ctrl+C pressed
Process asked to terminate
Child process exited
Invalid memory access occurred
CPU time limit exceeded
```

### Mental Model

```text
User / Kernel / Process
          │
          │ Signal
          ▼
     Target Process
          │
     ┌────┴─────┐
     ▼          ▼
Default      Custom
Action       Handler
     │
 ┌───┼────┐
 ▼   ▼    ▼
Stop Ignore Terminate
```

A signal is essentially the kernel telling a process:

> "An event happened. React to it."

---

# 2. Signals Are Asynchronous

Normally a program executes sequentially:

```text
Instruction
    ↓
Instruction
    ↓
Instruction
    ↓
Instruction
```

But a signal can arrive at almost any time:

```text
Instruction
    ↓
Instruction
    ↓
    ⚡ SIGINT arrives
    ↓
Signal handling
    ↓
Program continues / terminates
```

This is why signals are called **asynchronous notifications**.

---

# 3. Common Linux Signals

|Signal|Number|Purpose|
|---|--:|---|
|`SIGHUP`|1|Terminal closed / commonly used for reload|
|`SIGINT`|2|Interrupt (`Ctrl+C`)|
|`SIGKILL`|9|Force termination|
|`SIGTERM`|15|Request graceful termination|
|`SIGCONT`|18|Resume stopped process|
|`SIGSTOP`|19|Pause process|

View all signals:

```bash
kill -l
```

---

# 4. SIGINT — Interrupt

```text
SIGINT = Signal Interrupt
```

Usually generated by:

```text
Ctrl+C
```

Example:

```bash
sleep 1000
```

Press:

```text
Ctrl+C
```

Flow:

```text
Keyboard
   │
 Ctrl+C
   ↓
Terminal driver
   │
 SIGINT
   ↓
Foreground process/group
   │
   ▼
sleep terminates
```

Important:

> `Ctrl+C` itself doesn't directly kill the program. The terminal causes `SIGINT` to be sent.

---

# 5. SIGTERM — Graceful Termination

```text
SIGTERM = Signal Terminate
```

Number:

```text
15
```

Send using:

```bash
kill <PID>
```

`kill` sends `SIGTERM` by default.

Equivalent:

```bash
kill -TERM <PID>
```

or:

```bash
kill -15 <PID>
```

SIGTERM means:

> "Please terminate."

The process can catch SIGTERM and perform cleanup:

```text
SIGTERM
   ↓
Process
   ↓
Save state
Close files
Close sockets
Release resources
   ↓
Exit
```

Therefore SIGTERM is preferred when stopping processes normally.

---

# 6. SIGKILL — Forced Termination

```text
SIGKILL = Signal Kill
```

Number:

```text
9
```

Send:

```bash
kill -9 <PID>
```

or:

```bash
kill -KILL <PID>
```

SIGKILL means:

> "Terminate immediately."

The process **cannot catch, block, or ignore SIGKILL**.

Mental model:

```text
SIGTERM

Kernel
  ↓
Process
  ↓
"Please shut down"
  ↓
Process gets opportunity
to perform cleanup
```

vs.

```text
SIGKILL

Kernel
  ↓
Process terminated
```

### Why can't SIGKILL be ignored?

Because Linux needs a guaranteed mechanism for the kernel/system administrator to terminate a process.

If processes could ignore SIGKILL:

```text
Broken process
     ↓
Ignore everything
     ↓
Impossible to terminate
```

Therefore SIGKILL is enforced by the kernel rather than being handed to a user-defined signal handler.

---

# 7. SIGSTOP — Pause Process

```text
SIGSTOP = Signal Stop
```

Send:

```bash
kill -STOP <PID>
```

The process becomes stopped.

Check:

```bash
ps -o pid,state,cmd -p <PID>
```

You may see:

```text
PID   S   CMD
1234  T   sleep 300
```

`T` indicates a stopped process.

Like SIGKILL, **SIGSTOP cannot be caught or ignored**.

---

# 8. SIGCONT — Resume Process

```text
SIGCONT = Signal Continue
```

Resume a stopped process:

```bash
kill -CONT <PID>
```

Flow:

```text
Running
   │
 SIGSTOP
   ↓
Stopped
   │
 SIGCONT
   ↓
Running
```

# 9. SIGHUP

```text
SIGHUP = Signal Hang Up
```

Historically, SIGHUP indicated that a terminal connection was lost.

Today many daemons also interpret SIGHUP as:

> "Reload configuration."

Conceptually:

```text
Daemon running
      │
    SIGHUP
      ↓
Reload configuration
      │
Continue running
```

The exact behavior depends on the program.

---

# 10. The `kill` Command

Despite its name:

```bash
kill
```

doesn't necessarily **kill** anything.

Its real purpose is:

> Send a signal to a process.

Syntax:

```bash
kill -SIGNAL PID
```

Examples:

```bash
kill -TERM 1234
kill -KILL 1234
kill -STOP 1234
kill -CONT 1234
```

This is an important mental correction:

```text
kill command
     ≠
always kill

kill command
     =
send signal
```

---

# 11. What Can a Process Do With a Signal?

Depending on the signal, a process can:

```text
Signal arrives
      │
      ▼
┌───────────────────┐
│ Default behavior  │
│ Custom handler    │
│ Ignore            │
│ Block temporarily │
└───────────────────┘
```

A program can register a **signal handler**.

Conceptually:

```c
signal(SIGTERM, cleanup);
```

Then:

```text
SIGTERM arrives
      ↓
Kernel notices signal
      ↓
Process's signal handler runs
      ↓
cleanup()
      ↓
Program exits
```

Exceptions include:

```text
SIGKILL
SIGSTOP
```

These cannot be caught or ignored.

# 13. Signal Flow Internally

Suppose:

```bash
kill -TERM 5000
```

Conceptually:

```text
Shell
  │
  │ kill command
  ▼
kill(5000, SIGTERM)
  │
  ▼
Linux Kernel
  │
  │ locate PID 5000
  │ check permissions
  │ mark signal pending
  ▼
Target Process
  │
  ▼
Signal delivered
  │
  ├── Default action
  ├── Handler
  └── Ignore
```

The kernel is responsible for **signal delivery**.

# 14. Connection to `/proc`

From Day 22:

```text
/proc/<PID>
```

represents a running process.

Signals let us **change/control the state of that process**.

Example:

```text
Process
   │
   ├── /proc/<PID> → inspect it
   │
   └── signals     → control/notify it
```

So these two topics fit together nicely:

```text
/proc → Observe process
Signals → Influence process
```

# 15. Connection to systemd

When stopping a service:

```bash
systemctl stop nginx
```

systemd normally attempts an orderly shutdown using signals according to the service configuration.

This connects:

```text
systemctl
   ↓
systemd
   ↓
signal/process control
   ↓
service process
```

Signals are therefore fundamental to Linux service management.

# ⚡ SIGTERM vs SIGKILL

||SIGTERM|SIGKILL|
|---|---|---|
|Number|15|9|
|Meaning|Please terminate|Terminate immediately|
|Can handle?|✅|❌|
|Can ignore?|✅|❌|
|Cleanup possible?|✅|❌ handler opportunity|
|Typical use|Normal shutdown|Last resort|

> [!important]  
> Prefer **SIGTERM first**. Use **SIGKILL when a process will not terminate normally**.
