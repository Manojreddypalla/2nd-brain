# Linux Internals — Day 20

## Linux Boot Process: Power Button → Login Prompt

### 🎯 Goal

Understand:

```text
Power
  ↓
Firmware
  ↓
Bootloader
  ↓
Kernel
  ↓
initramfs
  ↓
Real Root Filesystem
  ↓
systemd (PID 1)
  ↓
Services
  ↓
Login / Desktop
```

The important question throughout this topic is:

> **Who currently controls the machine, and what must they prepare before handing control to the next stage?**

---

# 1. The Big Picture

When you press the power button, Linux itself **doesn't immediately start**.

At first, there isn't even a running operating system.

The machine progresses through several layers:

```text
Hardware
   ↓
BIOS / UEFI
   ↓
GRUB
   ↓
Linux Kernel
   ↓
initramfs
   ↓
systemd
   ↓
Services
   ↓
Login
```

Each layer solves a problem that the next layer cannot initially solve for itself.

For example:

```text
Kernel is stored on disk
        ↓
But kernel isn't running yet
        ↓
So something else must load it
        ↓
GRUB loads the kernel
```

And:

```text
Real root filesystem may require drivers
        ↓
Drivers/modules may live inside root filesystem
        ↓
But root isn't mounted yet!
        ↓
initramfs provides the required early environment
```

That second situation is especially important.

---

# 2. Stage 0 — Power On

You press:

```text
POWER
```

The CPU begins executing instructions from a predefined firmware location.

At this point:

```text
No Linux
No systemd
No shell
No processes
No filesystem mounted
```

The system firmware takes control.

Depending on the machine, this is usually:

```text
BIOS
```

or modern:

```text
UEFI
```

---

# 3. BIOS / UEFI

## What is BIOS?

**BIOS = Basic Input/Output System**

Older computers commonly use BIOS.

Its job is to initialize enough hardware to start the boot process.

Think:

```text
Power
 ↓
BIOS wakes up
 ↓
Check hardware
 ↓
Find something bootable
```

BIOS performs hardware initialization/testing, traditionally including POST:

**POST = Power-On Self-Test**

It checks/initializes things such as:

```text
CPU
RAM
Keyboard
Storage controllers
Other basic hardware
```

Then it searches the configured boot order.

Example:

```text
1. NVMe SSD
2. SATA SSD
3. USB
4. Network
```

---

# 4. Legacy BIOS Boot

Traditional BIOS does not understand modern Linux filesystems in the way Linux itself does.

Instead, it loads boot code from the boot disk.

Historically this involved the:

```text
MBR
```

**MBR = Master Boot Record**

The MBR occupies the first sector of a traditional BIOS-partitioned boot disk and contains bootstrapping information/code.

Conceptually:

```text
BIOS
 ↓
Boot disk
 ↓
Boot code
 ↓
GRUB
```

GRUB then takes over.

---

# 5. UEFI

**UEFI = Unified Extensible Firmware Interface**

UEFI is the modern replacement for legacy BIOS.

Most modern machines use it.

Instead of relying on MBR boot code in the old BIOS style, UEFI can load boot applications from a special partition:

```text
EFI System Partition
```

usually abbreviated:

```text
ESP
```

The ESP commonly uses FAT32.

Conceptually:

```text
UEFI
 ↓
EFI System Partition
 ↓
EFI boot program
 ↓
GRUB
```

On a Linux installation you might find EFI files around:

```bash
/boot/efi/
```

depending on the distribution and mount configuration.

---

# 6. BIOS vs UEFI

|BIOS|UEFI|
|---|---|
|Older firmware model|Modern firmware model|
|Traditional MBR-style booting|Loads EFI applications|
|Limited legacy environment|More capable firmware environment|
|Often associated with MBR|Commonly associated with GPT|
|Legacy boot|Modern standard|

Don't memorize BIOS and UEFI as completely different boot processes.

Their common purpose here is:

> **Initialize the machine and locate something capable of booting the operating system.**

---

# 7. Stage 2 — GRUB

After firmware has done its job, we need something capable of loading Linux.

That's the **bootloader**.

A common Linux bootloader is:

```text
GRUB
```

**GRUB = GNU GRand Unified Bootloader**

GRUB's central job is:

> Find and load the Linux kernel and its early userspace image, then transfer control to the kernel.

---

# 8. Why Do We Need a Bootloader?

The kernel exists as a file on storage.

For example:

```text
/boot/vmlinuz-...
```

But here's the problem:

```text
Kernel exists on disk

BUT

Kernel isn't running
```

So it cannot simply load itself.

Something already running must:

```text
Locate kernel
      ↓
Load kernel into RAM
      ↓
Supply boot parameters
      ↓
Start kernel
```

That's the bootloader's job.

---

# 9. GRUB Menu

You've probably seen something similar to:

```text
Ubuntu
Advanced options for Ubuntu
Windows Boot Manager
```

GRUB can allow you to select:

```text
Different OS
Different kernel versions
Recovery mode
Older kernels
```

This becomes extremely useful when a kernel upgrade breaks something.

You can potentially boot:

```text

Kernel 6.x-old
Recovery
```

---

# 10. Kernel Command-Line Parameters

GRUB doesn't merely load the kernel.

It can also provide **kernel parameters**.

You can inspect the parameters used for your current boot:

```bash
cat /proc/cmdline
```

You might see something resembling:

```text
BOOT_IMAGE=...
root=UUID=...
ro
quiet
splash
```

For example:

```text
root=UUID=...
```

tells the boot process which filesystem/device should become the root filesystem.

So conceptually:

```text
GRUB
 ├── loads kernel
 ├── loads initramfs
 └── supplies kernel arguments
```

---

# 11. Stage 3 — Linux Kernel Starts

Now GRUB transfers control to the Linux kernel.

This is a major transition:

```text
Firmware
   ↓
Bootloader
   ↓
====================
     KERNEL
====================
```

The actual operating-system kernel is now running.

---

# 12. What Does the Kernel Initialize?

During early boot, the kernel begins establishing the core systems you've studied throughout Linux Internals.

It initializes things such as:

```text
CPU management
Memory management
Interrupt handling
Device infrastructure
Drivers
Storage subsystem
Process infrastructure
Filesystems
Networking infrastructure
```

Notice how your previous topics connect.

### Memory

The kernel discovers available physical memory and initializes memory management.

```text
Physical RAM
     ↓
Kernel memory management
     ↓
Virtual memory / pages / allocators
```

### Hardware

The kernel detects devices and loads/binds available drivers.

```text
PCI devices
Storage
USB
Network devices
GPU
etc.
```

### Filesystem

Eventually Linux needs:

```text
/
```

the real root filesystem.

But this introduces an interesting bootstrapping problem.

---

# 13. The Root Filesystem Problem

Imagine your Linux root filesystem is:

```text
/dev/nvme0n1p2
```

and uses:

```text
ext4
```

The kernel needs the appropriate storage and filesystem support to access it.

Things become more complicated with setups such as:

```text
LVM
RAID
Disk encryption
Special storage controllers
Network root
```

The system may need extra kernel modules or userspace tools **before the real root filesystem can be mounted**.

But those files normally live on the root filesystem.

So:

```text
Need files to mount root
        ↓
Files are stored inside root
        ↓
Can't access files until root is mounted
```

Classic chicken-and-egg problem.

The solution is:

# initramfs

---

# 14. What Is initramfs?

**initramfs = initial RAM filesystem**

It is a small temporary filesystem/environment made available during early boot.

It contains enough components to prepare access to the real root filesystem.

Think of it as:

> A tiny temporary rescue/boot environment used before the real Linux userspace is available.

---

# 15. What Might initramfs Contain?

Depending on the system:

```text
Kernel modules
Storage drivers
Filesystem support
LVM tools
RAID tools
Encryption tools
Early userspace programs/scripts
```

Example:

Suppose your root filesystem is encrypted.

Linux cannot simply do:

```text
mount /
```

It may first need:

```text
Load storage support
      ↓
Find encrypted volume
      ↓
Request/deal with decryption
      ↓
Unlock volume
      ↓
Locate root filesystem
      ↓
Mount it
```

initramfs provides the early environment necessary to perform this work.

---

# 16. Kernel vs initramfs

This distinction matters.

### Kernel

The kernel provides the fundamental OS mechanisms:

```text
Memory
Processes
Drivers
Scheduling
Filesystems
Networking
```

### initramfs

initramfs provides an **early temporary userspace/filesystem** needed to reach the real root filesystem.

Mental model:

```text
Kernel = engine

initramfs = temporary toolkit
```

---

# 17. Switching to the Real Root Filesystem

Initially:

```text
Kernel
   ↓
initramfs
```

The early boot environment locates/prepares the actual root filesystem.

Then Linux transitions to it.

Conceptually:

```text
Temporary root
(initramfs)

      ↓

Find real root

      ↓

Mount real root

      ↓

Switch root

      ↓

Real /
```

Now the normal Linux userspace can start.

---

# 18. Stage 5 — systemd

Once the real root filesystem is available, the kernel starts the configured userspace init program.

On most modern mainstream Linux distributions this is:

```text
systemd
```

And systemd becomes:

```text
PID 1
```

Check:

```bash
ps -p 1 -f
```

Example:

```text
UID   PID  PPID CMD
root    1     0 /sbin/init
```

On systemd systems, `/sbin/init` commonly resolves to systemd.

Try:

```bash
readlink -f /sbin/init
```

---

# 19. Why Is systemd PID 1?

The kernel creates/starts the first userspace process during normal boot.

That process receives:

```text
PID 1
```

On a systemd-based Linux distribution, that process is systemd.

Therefore:

```text
Kernel space
     ↓
systemd
PID = 1
     ↓
rest of userspace
```

This is why systemd is special.

It isn't merely another background service.

It's the userspace init/service manager at the root of the normal process hierarchy.

---

Normal idea:

```text
  ↓

  ↓

```

At the top of userspace:

```text

```

You can visualize processes with:

# 21. What Does systemd Do?

systemd manages the transition from:

```text
Kernel successfully booted
```

to:

```text
Usable Linux system
```

It starts/manages units needed for the configured system state.

These can involve:

```text
Filesystems
Networking
Logging
Device-related services
Timers
Sockets
Login services
Display manager
Other daemons
```

---

# 22. systemd Units

systemd organizes resources using **units**.

Common types include:

```text
.service
.socket
.target
.mount
.timer
.device
.path
```

Examples:

```text
sshd.service
NetworkManager.service
multi-user.target
graphical.target
```

A `.service` generally describes a service.

A `.target` groups/synchronizes units toward a particular system state.

---

# 23. systemd Targets

Older SysV init systems commonly used the idea of:

```text
runlevels
```

systemd uses **targets**.

Important examples:

```text
multi-user.target
graphical.target
rescue.target
emergency.target
```

### multi-user.target

Generally represents a usable multi-user non-graphical system state.

Think:

```text
Server / terminal-oriented system
```

### graphical.target

Includes what's needed for a graphical environment.

Conceptually:

```text
multi-user environment
       +
graphical login/display stack
```

Check your default:

```bash
systemctl get-default
```

You might get:

```text
graphical.target
```

---

# 24. Dependencies

systemd does **not** simply execute every service one by one.

Units have dependencies and ordering relationships.

Conceptually:

```text
graphical.target
        ↓
needs other units
        ↓
those units need others
```

Some independent work can happen in parallel.

That's why the real boot process looks less like:

```text
A → B → C → D → E
```

and more like:

```text
        A
       / \
      B   C
      |   |
      D   E
       \ /
        F
```

That mental model will help with:

```bash
systemd-analyze critical-chain
```

---

# 25. Stage 6 — System Services

systemd starts the units required for the desired target.

Depending on your machine:

```text
Networking
Bluetooth
Audio
SSH
Logging

Other daemons
```

Eventually the system reaches the configured target.

For a desktop:

```text
graphical.target
```

For many server setups:

```text

```

# 26. Stage 7 — Login

Finally the system provides a way for you to log in.

That might be a text terminal:

```text
login:
```

or a graphical display manager such as GDM/SDDM/LightDM, depending on the desktop.

After authentication, your user session starts.

For a terminal login:

```text
Login
 ↓
User session
 ↓
Shell
 ↓
bash / zsh / etc.
```

For a desktop:

```text
Display Manager
      ↓
Login
      ↓
Desktop Session
      ↓
GNOME / KDE / etc.
```

Now the system feels "booted."

# 35. systemd-analyze blame

Run:

```bash
systemd-analyze blame
```

This lists units by how long their activation took.

Example:

```text
8.2s NetworkManager-wait-online.service
3.1s docker.service
1.8s bluetooth.service
...
```

This helps answer:

> Which units took a long time to activate?

But be careful:

**Slow unit ≠ necessarily the cause of the total boot delay.**

Why?

Because services can run in parallel.

```text
Service A ────────────── 10 sec

Service B ─── 3 sec
Service C ───── 5 sec
```

A service taking 10 seconds doesn't automatically mean it added 10 seconds to the final boot time.

For that, dependencies matter.

---

# 36. Critical Chain

Run:

```bash
systemd-analyze critical-chain
```

This is more interesting.

It tries to show the time-critical dependency path leading toward the boot target.

Think of it like finding the longest important dependency chain:

```text
graphical.target
      ↑
display-manager.service
      ↑
network.target
      ↑
some.service
```

If one critical dependency is delayed, everything depending on it may also be delayed.

This connects directly to graphs.

systemd's dependency structure can be thought of as a:

```text
Dependency Graph
```

Nodes:

```text
services / targets / mounts / sockets
```

Edges:

```text
dependencies / ordering
```

So boot analysis is partly a **graph traversal/dependency problem**.

# 41. Common Boot Failure Mental Model

If Linux fails to boot, first ask:

> **How far did the machine get?**

### No firmware screen

Think:

```text
Hardware / firmware
```

### Firmware works, bootloader missing

Think:

```text
Boot device
EFI configuration
GRUB
```

### GRUB appears, kernel fails

Think:

```text
Kernel
Kernel parameters
Drivers
```

### Kernel runs but root can't mount

Think:

```text
initramfs
Storage driver
Filesystem
Encryption
LVM
Root device
```

### Root mounts but services fail

Think:

```text
systemd
Units
Dependencies
Configuration
```

### System works but GUI doesn't appear

Think:

```text
Display manager
GPU/display stack
graphical.target
Desktop environment
```

This is a much better debugging method than randomly trying commands.

# 42. Interview / Exam Questions

### Q1. What is the role of BIOS/UEFI?

It initializes essential hardware and locates/starts the next boot component.

---

### Q2. Why is GRUB needed?

GRUB loads the Linux kernel and initramfs into memory, supplies kernel parameters, and transfers control to the kernel.

---

### Q3. What does the kernel do during boot?

It initializes core OS mechanisms including CPU handling, memory management, drivers, devices, filesystems and other kernel subsystems, then enables the transition toward userspace.

---

### Q4. Why is initramfs needed?

It provides a temporary early userspace/filesystem containing the tools and modules necessary to prepare and mount the real root filesystem.

---

### Q5. Why is systemd PID 1?

The kernel starts the init process as the first normal userspace process. On systemd-based distributions that init system is systemd, so it receives PID 1.

---

### Q6. Does systemd start before the kernel?

No.

```text
Kernel
 ↓
systemd
```

systemd is a userspace program.

---

### Q7. Does GRUB remain running after Linux starts?

No. It performs its bootloader job and transfers control to the kernel.

---

### Q8. Is initramfs the actual root filesystem?

No.

It's an early temporary root environment used to prepare/access the real root filesystem.

# 🧠 Final Mental Model

Don't memorize:

> BIOS → GRUB → Kernel → initramfs → systemd.

Instead remember the **problem each stage solves**:

```text
BIOS / UEFI
"How do I initialize the machine
 and find something bootable?"
          ↓

GRUB
"How do I get the kernel into RAM
 and start it?"
          ↓

KERNEL
"How do I turn this hardware
 into a functioning operating system?"
          ↓

INITRAMFS
"How do I prepare/access the real root
 before normal userspace exists?"
          ↓

SYSTEMD
"How do I bring userspace into
 the required operating state?"
          ↓

LOGIN
"How does a user start a session?"
```

And the deeper picture is:

```text
                    POWER
                      │
                      ▼
              ┌──────────────┐
              │  BIOS / UEFI │
              │   Firmware   │
              └──────┬───────┘
                     │
               find bootloader
                     │
                     ▼
              ┌──────────────┐
              │     GRUB     │
              │  Bootloader  │
              └──────┬───────┘
                     │
          kernel + initramfs + args
                     │
                     ▼
              ┌──────────────┐
              │ Linux Kernel │
              └──────┬───────┘
                     │
       CPU ───────────┤
       Memory ────────┤
       Drivers ───────┤
       Devices ───────┤
                     │
                     ▼
              ┌──────────────┐
              │   initramfs  │
              └──────┬───────┘
                     │
              prepare real /
                     │
                     ▼
              ┌──────────────┐
              │   systemd    │
              │    PID 1     │
              └──────┬───────┘
                     │
              dependency graph
                     │
          ┌──────────┼──────────┐
          ▼          ▼          ▼
      Network     Logging     Services
          └──────────┼──────────┘
                     ▼
                  LOGIN
                     │
                     ▼
              SHELL / DESKTOP
```

**Day 20 takeaway:** Linux boot is fundamentally a sequence of **progressive initialization and control transfer**. Firmware knows enough to start a bootloader; the bootloader knows enough to start the kernel; the kernel plus initramfs know enough to reach the real root filesystem; and systemd knows how to construct the full userspace environment.
