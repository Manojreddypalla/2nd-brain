# JWT (JSON Web Token) — From Scratch

> **One-line definition:** A JWT is a **digitally signed identity card** that the client carries and presents to the server on every request.

---

# Step 1: The Problem

HTTP is stateless.

```text
Request 1
↓

Server

↓

Response

Request 2

↓

Server

↓

"Who are you?"
```

The server forgets every request.

So websites need a way to remember users.

There are two common solutions:

1. **Sessions**
    
2. **JWT**
    

---

# Step 2: Session Authentication (Traditional Way)

## Login

```text
Username + Password
        │
        ▼
Server verifies credentials
        │
        ▼
Creates Session
        │
        ▼
Session ID = ABC123
        │
        ▼
Stores session on server
        │
        ▼
Sends cookie:
sessionId=ABC123
```

Browser stores:

```text
sessionId=ABC123
```

Server stores:

```text
ABC123
   │
   ├── User ID = 101
   ├── Name = Manoj
   ├── Role = Admin
   └── Cart
```

### Every request

Browser sends:

```http
Cookie:
sessionId=ABC123
```

Server:

```text
Find session ABC123

↓

Found

↓

Allow request
```

# Step 3: What's the Problem with Sessions?

Imagine millions of users.

Server stores:

```text
ABC123
DEF456
XYZ999
AAA222
BBB333
...
Millions of sessions
```

If you have multiple servers:

```text
        Load Balancer
              │
      ┌───────┴────────┐
      │                │
 Server A          Server B
```

If Server A created your session but your next request goes to Server B:

```text
Server B

↓

"I don't have session ABC123."
```

To fix this, companies often use shared session storage like Redis.

---

# Step 4: JWT Solves This Differently

Instead of storing everything on the server:

The server creates a signed token.

```text
Server

↓

Creates JWT

↓

Sends JWT

↓

Browser Stores JWT
```

The server doesn't need to store a session for every user.

---

# Step 5: What's Inside a JWT?

A JWT has three parts.

```text
HEADER.PAYLOAD.SIGNATURE
```

Think of it as:

```text
Instructions

↓

Information

↓

Official Signature
```

---

## Header

Tells the server how the token was signed.

Example:

```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```

---

## Payload

Contains user information.

Example:

```json
{
  "userId": 101,
  "name": "Manoj",
  "role": "Admin"
}
```

**Anyone who has the JWT can decode and read this.**

So never put:

- Passwords
    
- Credit card numbers
    
- Secrets
    

inside the payload.

---

## Signature

This is the most important part.

The server creates it using:

```text
Header

+

Payload

+

Secret Key

↓

Signature
```

The secret key never leaves the server.

# Step 7: Every Request

Browser sends:

```http
Authorization:

Bearer eyJhb...
```

Server:

```text
Receive JWT

↓

Verify Signature

↓

Valid?

↓

YES

↓

Allow request
```

Notice:

The server **doesn't look up a session**.

It simply verifies the token.

---

# Step 8: Can Someone Change the JWT?

Suppose the payload says:

```json
{
    "role":"user"
}
```

Attacker changes it:

```json
{
    "role":"admin"
}
```

Looks dangerous.

But the signature was created using the **original payload**.

When the server checks:

```text
Payload

↓

Signature

↓

Match?

↓

NO
```

Result:

```text
401 Unauthorized
```

So:

✅ JWT can be **read**.

❌ JWT cannot be **modified successfully**.

---

# Step 9: Sessions vs JWT

|Feature|Session|JWT|
|---|---|---|
|Browser stores|Session ID|JWT|
|Server stores|Session data|Usually nothing for authentication|
|Every request|Session ID|JWT|
|Server action|Look up session|Verify signature|
|Scaling|Needs shared session store|Easy across many servers|
|Logout|Delete session|Token stays valid until it expires (unless you add a revocation mechanism)|

# Step 11: Where Is JWT Stored?

JWT itself doesn't decide where it's stored.

Common choices:

```text
Browser

↓

HttpOnly Cookie

OR

Memory

OR

Local Storage
```

JWT is **the token**, not the storage method.

---

# Step 12: Why Companies Use JWT

Great for:

- REST APIs
    
- Mobile apps
    
- Microservices
    
- Distributed systems
    

Because any server with the signing key can verify the token.

```text
Browser
      │
      ▼
Load Balancer
      │
 ┌────┴────┐
 │         │
API A    API B

Both can verify the JWT.
```

No shared session database is required just to authenticate the user.

# Interview Questions

### What is JWT?

A signed token used to authenticate and authorize users.

---

### Is JWT encrypted?

No. It's **signed**, not encrypted, by default.

---

### Can anyone read a JWT?

Yes, the header and payload can be decoded.

---

### Can anyone modify a JWT?

They can edit it, but the server will reject it because the signature won't match.

---

### Does the server store JWT?

Not usually for authentication. It only needs the signing key to verify tokens.

---

# One Sentence to Remember

- **Session:** "The server remembers you."
    
- **JWT:** "You carry proof of who you are."
    

That single comparison is often the easiest way to distinguish the two.
