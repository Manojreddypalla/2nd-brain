# GraphQL

> **Interview Importance:** ⭐⭐⭐⭐☆
> 
> **One-line definition:** **GraphQL** is a **query language and runtime for APIs** that lets the client request **exactly the data it needs**.

---

# Full Form

**GraphQL**

Despite the name, it has **nothing to do with graphs (DSA)**.

- **Graph** → Represents relationships between data (Users → Posts → Comments).
    
- **QL** → Query Language.
    

---

# Why Was GraphQL Created?

Imagine you're building Instagram.

Your homepage needs:

- User name
    
- Profile picture
    
- Latest 5 posts
    

With REST:

```text
GET /users/101

↓

Returns ALL user data
```

Then

```text
GET /posts?user=101
```

Two requests.

Maybe even more.

---

# Problem with REST

Suppose REST returns:

```json
{
  "id":101,
  "name":"Manoj",
  "email":"abc@gmail.com",
  "phone":"123456789",
  "address":"India",
  "age":22,
  "gender":"Male"
}
```

But your page only needs:

```text
Name
```

You downloaded lots of unnecessary data.

This is called **Over-fetching**.

---

Another problem:

Need:

- User
    
- Posts
    
- Comments
    

REST:

```text
GET /users/101

GET /posts

GET /comments
```

Three requests.

This is called **Under-fetching** because one request isn't enough.

---

# GraphQL Solution

Client asks only for what it needs.

Example:

```graphql
{
  user(id:101){
    name
    profilePicture
  }
}
```

Server returns:

```json
{
  "data":{
    "user":{
      "name":"Manoj",
      "profilePicture":"img.png"
    }
  }
}
```

Nothing extra.

# Nested Data

GraphQL shines here.

Example:

```graphql
{
 user(id:101){
    name
    posts{
        title
        likes
    }
 }
}
```

One request.

Response:

```json
{
 "user":{
   "name":"Manoj",
   "posts":[]
 }
}
```

REST might require multiple API calls.

# CRUD

GraphQL doesn't use GET/POST/PUT/DELETE the same way REST does.

Instead, it has:

## Query

Read data.

```graphql
query{
 user(id:1){
   name
 }
}
```

---

## Mutation

Change data.

```graphql
mutation{
 createUser(name:"Manoj"){
    id
 }
}
```

---

## Subscription

Real-time updates.

```graphql
subscription{
 newMessage{
    text
 }
}
```

Similar in purpose to WebSockets for pushing updates.

# REST vs GraphQL

|REST|GraphQL|
|---|---|
|Many endpoints|Usually one endpoint|
|Server decides response|Client chooses fields|
|Can over-fetch|No over-fetching|
|Can under-fetch|Usually one request is enough|
|Uses HTTP verbs|Uses Queries & Mutations|

# Interview Questions

### What is GraphQL?

A query language and runtime for APIs that allows clients to request exactly the data they need.

---

### Is GraphQL a database?

❌ No.

It is an API technology.

---

### Does GraphQL replace HTTP?

❌ No.

It usually runs **over HTTP**.

---

### Why is GraphQL faster?

Not because it's inherently faster.

It often reduces:

- Number of API requests
    
- Amount of unnecessary data transferred

# ⭐ The Big Picture

You've now learned three ways applications communicate:

```text
Browser
    │
    ▼
HTTP
    │
    ├── REST
    │      └── Multiple endpoints
    │
    └── GraphQL
           └── Single endpoint
```

- **HTTP** = The road (communication protocol)
    
- **REST** = One style of designing APIs
    
- **GraphQL** = Another style where the **client controls the response**
    

## 🧠 Easy Memory Trick

- **REST** → _"Server decides what to send."_
    
- **GraphQL** → _"Client decides what to receive."_
    

That's the key difference interviewers are usually looking for.
