# Operating Systems — Lecture 1 Full Notes

## 1. What is an Operating System?

Before defining an OS, understand the problem it solves.

Suppose we write:

```c
int main() {
    int a = 1;
    int b = 2;
    int c = a + b;
}
```

There are several stages before the CPU can execute this program.

```text
Source Code
    ↓
Compiler
    ↓
Executable (a.out)
    ↓
Loaded into Main Memory
    ↓
CPU executes instructions
```

The slides illustrate exactly this source → executable → memory → CPU journey.

The important distinction is:

```text
Program stored on disk
        ↓
     LOAD
        ↓
Program placed in RAM
        ↓
CPU executes it
```

A program sitting on disk is not automatically executing.

---

# 2. Executable and Memory Layout

After compilation, the executable contains things such as:

```text
Executable
┌──────────────┐
│    Data      │
├──────────────┤
│ Instructions │
└──────────────┘
```

When loaded into memory, the program's memory contains regions conceptually shown in the lecture as:

```text
High Address
0xFFF...
┌──────────────┐
│      OS      │
├──────────────┤
│    Stack ↓   │
│              │
│    Heap ↑    │
├──────────────┤
│     Data     │
├──────────────┤
│ Instructions │
└──────────────┘
0x000...
Low Address
```

Meanwhile, the CPU contains registers, including the **Program Counter (PC)**.

# 4. Inside the CPU

Conceptually, the CPU contains:

```text
CPU
┌─────────────────┐
│  Control Unit   │
├─────────────────┤
│      ALU        │
├─────────────────┤
│    Registers    │
└─────────────────┘
```

### ALU

**Arithmetic Logic Unit**

Performs arithmetic and logical operations.

For example:

```text
a + b
```

The actual computation is ultimately performed by CPU hardware such as the ALU.

### Control Unit

Coordinates instruction execution.

### Registers

Very small, very fast storage locations inside the CPU.

One particularly important register for OS is the:

# Program Counter — PC

The **PC contains the address of the next instruction to execute.**

Mental model:

```text
Memory

1000 → instruction 1
1001 → instruction 2
1002 → instruction 3
1003 → instruction 4
         ↑
       PC
```

If:

```text
PC = 1002
```

the CPU knows where its next instruction comes from.

The lecture explicitly introduces the PC as the register telling the CPU the address of the next instruction.

---

# 5. Fetch–Decode–Execute Cycle

The CPU continuously performs:

```text
FETCH
  ↓
DECODE
  ↓
EXECUTE
  ↓
FETCH
  ↓
...
```

### Fetch

Get the instruction identified by the PC.

### Decode

Determine what that instruction means.

For example:

```text
ADD R1, R2
```

### Execute

Actually perform the operation.

Then the CPU continues with the next instruction.

The key intuition from the lecture is that this is effectively a continuous cycle.

---

# 6. Does the CPU Stop When a Program Finishes?

No.

This is a very useful OS mental model.

Suppose:

```text
Program A instructions
Program A instructions
Program A instructions
        ↓
Program A finishes
```

The CPU doesn't say:

> “Done. I'll stop now.”

Instead, control eventually goes elsewhere—typically back to operating-system code—and the CPU continues fetching instructions.

From the CPU's perspective, it may look like:

```text
OS instruction
OS instruction
OS instruction
Program A instruction
Program A instruction
Program B instruction
OS instruction
...
```

The CPU itself just keeps executing instructions.

This idea becomes extremely important later when learning:

```text
System Calls
Interrupts
Processes
Context Switching
Scheduling
```

# 7. Can We Run a Program Without an OS?

The lecture asks us to imagine doing exactly that.

Suppose:

```c
int a = 1;
int b = 2;
int c = a + b;
```

We want to run this directly on hardware without an OS.

At minimum:

### Step 1 — Put the program in memory

Suppose it begins at address:

```text
1000
```

### Step 2 — Set the PC

We need to tell the CPU where execution starts:

```text
PC = 1000
```

### Step 3 — CPU executes

Now:

```text
PC
 ↓
1000 → instruction
1001 → instruction
1002 → instruction
...
```

using the fetch–decode–execute cycle.

### Step 4 — Obtain the result

For pure computation this looks manageable.

The lecture summarizes this process as loading the program at some address, setting the PC to the program, and letting the CPU execute it.

But now things get ugly.

---

# 8. Problem #1 — I/O

Suppose the program contains:

```c
printf("Hello");
```

Now we want something to appear on the monitor.

But:

```text
CPU ≠ Monitor
```

They are different hardware devices.

The CPU cannot magically understand:

```c
printf("Hello");
```

as “put these pixels on that monitor.”

The machine must interact with hardware/controller mechanisms.

Without an OS, the programmer would need to handle these hardware details manually.

Conceptually:

```text
Program
   ↓
CPU
   ↓
Hardware interaction
   ↓
Monitor
```

The slides use monitor output as the first concrete example of why raw hardware interaction becomes painful.

---

# 9. Problem #2 — Multiple Programs

Now suppose we want:

```text
Program A
Program B
Program C
Program D
```

to run.

Questions immediately appear:

```text
Who runs first?

How long can A use the CPU?

When should B run?

Who pauses A?

Who resumes A?

What if one program never stops?
```

Without an OS, somebody must manually coordinate all of this.

This is the **CPU management / scheduling problem**.

---

# 10. Problem #3 — Memory

Suppose:

```text
Program A
Program B
```

are both loaded into RAM.

RAM is shared physical hardware.

Now we must answer:

```text
Where does A begin?

Where does A end?

Where does B begin?

How does B know its allowed memory?

What prevents A from overwriting B?
```

Conceptually:

```text
RAM

┌─────────────┐
│ Program A   │
├─────────────┤
│ Program B   │
├─────────────┤
│ Other data  │
└─────────────┘
```

Without management/protection, one program could accidentally or maliciously interfere with another.

Hence we need:

**Memory Management + Protection**

The lecture introduces this as the shared-memory problem between programs.

---

# 11. Problem #4 — Storage

RAM is volatile.

```text
Power OFF
   ↓
RAM contents lost
```

So permanent data must live on storage such as a disk.

But a raw disk is essentially storage hardware.

We want abstractions such as:

```text
notes.txt
photo.jpg
project/
documents/
```

not:

```text
sector 92817
sector 92818
sector 92819
```

Without an OS we'd have to manage questions like:

```text
Where is my file physically stored?

Which disk sectors are free?

Which sectors belong together?

How do I locate a file?

How do I create/delete files?
```

This motivates the:

# File System

The storage slide explicitly connects raw disk management with the need for a filesystem.

---

# 12. Life Without an OS

Without an OS, every application might need to deal with things like:

```text
Monitor hardware/register details
Keyboard input handling
Disk geometry/storage details
Network-card buffers
Memory management
CPU sharing
Security/protection
```

That would mean every programmer repeatedly solves the same hardware-management problems.

So instead:

```text
            Applications
                 ↓
        ┌─────────────────┐
        │ Operating System│
        └─────────────────┘
                 ↓
 ┌─────┬────────┬────────┬───────┐
 │ CPU │ Monitor│Keyboard│ Disk  │
 └─────┴────────┴────────┴───────┘
              Hardware
```

The OS becomes the layer managing hardware/resources on behalf of programs.

---

# 13. Why Do We Need an Operating System?

Now we can derive the answer rather than memorize it.

The CPU is excellent at:

```text
✓ calculations
✓ following instructions
✓ executing programs
```

But the CPU alone doesn't conveniently provide:

```text
✗ file management
✗ memory allocation/management
✗ CPU sharing among programs
✗ convenient I/O-device control
```

That is where the operating system comes in.

So a useful mental model is:

> **CPU = worker**

> **OS = manager**

The CPU does the actual execution.

The OS manages **what gets executed and how machine resources are used**.

---

# 14. OS as Resource Manager

The major resources include:

```text
CPU
Memory
Storage
I/O devices
```

The OS manages access to them.

Therefore:

```text
                    Operating System
                          │
        ┌─────────────────┼─────────────────┐
        ↓                 ↓                 ↓
       CPU              Memory           Devices
        ↓                                   ↓
   Scheduling                         I/O management

                          ↓
                       Storage
                          ↓
                     File System
```

The lecture's “big picture” slide summarizes OS responsibilities around device, CPU, storage and security management.

# 15. OS Provides Abstraction

There's another important idea hiding underneath all this.

Applications don't want to understand every piece of hardware.

Instead of thinking:

```text
physical disk sectors
```

we think:

```text
file
```

Instead of thinking:

```text
raw CPU execution
```

we think:

```text
process
```

Instead of directly manipulating physical memory:

```text
memory abstraction
```

And instead of directly controlling device registers:

```text
OS/device interface
```

So conceptually:

```text
Ugly hardware details
        ↓
Operating System
        ↓
Clean abstractions
        ↓
Applications
```

That is one of the deepest reasons OS exists.

# 16. Manual Work Without an OS

The lecture boils down the manual burden to things such as:

```text
1. Set the PC manually

2. Grant permission/access to hardware manually

3. Ensure programs don't overwrite/interfere with each other

4. Manage program loading/reloading

5. Coordinate concurrent programs
```

Doing this once might be possible.

Doing it for every application is ridiculous.

So instead of every programmer implementing the same machinery:

```text
Programmer A ─┐
Programmer B ─┤
Programmer C ─┼──→ common management software
Programmer D ─┤
              ↓
        Operating System
```

This is how the lecture motivates the existence of OS.

# 17. CPU Virtualization

Now the lecture introduces one of the most important OS ideas:

# Virtualizing the CPU

Consider four programs:

```text
A
B
C
D
```

Each contains an infinite loop:

```c
while (1) {
    printf(...);
}
```

The slides run multiple such programs and show their outputs appearing together.

Suppose the machine has:

```text
1 CPU
```

Yet output looks roughly like:

```text
A
B
C
A
D
B
A
C
...
```

It appears as though:

```text
A + B + C + D
```

are running simultaneously.

But with one CPU/core, only one instruction stream can actually be executing on that CPU at an instant.

So what's happening?

---

# 18. Interleaving

The OS rapidly switches CPU execution among programs.

Conceptually:

```text
Time ───────────────────────────────→

CPU:

| A | B | A | C | B | D | A | C |
```

Program A gets some CPU time.

Then Program B.

Then C.

Then A again.

And so on.

Because switching happens rapidly, the programs **appear** to execute simultaneously.

The lecture's timeline diagram calls this interleaving/multiprogramming on one processor.

---

# 19. Context Switch — Initial Intuition

Suppose the CPU is executing:

```text
Program A
```

and the OS wants to execute:

```text
Program B
```

It can't simply forget everything A was doing.

A has execution state.

Conceptually:

```text
A running
   ↓
save A's state
   ↓
load B's state
   ↓
B running
```

Later:

```text
B running
   ↓
save B's state
   ↓
restore A's state
   ↓
A continues
```

This switching of execution between processes is associated with a:

# Context Switch

The slide explicitly labels the transitions in the interleaving diagram as context switches.

You'll study the exact saved state later.

For now, think:

> **Context = enough information to resume execution later.**

# 20. CPU Scheduling

Now somebody has to decide:

```text
Who gets CPU?
```

That is:

# CPU Scheduling

Example:

```text
Time →

| P1 | P2 | P1 | P3 | P2 | P1 |
```

The operating system's scheduler determines which process gets CPU time.

Later algorithms include things like:

```text
FCFS
Round Robin
...
```

The final lecture slide explicitly lists process scheduling with examples such as FCFS and RR.

---

# 21. CPU Virtualization — The Illusion

This gives us the central idea.

Physical reality:

```text
             ONE CPU
                │
                ↓
        one execution stream
        at a particular instant
```

OS-created illusion:

```text
      P1    P2    P3    P4
       ↓     ↓     ↓     ↓
      CPU   CPU   CPU   CPU
```

Each process behaves as if it has access to a CPU.

But underneath:

```text
Physical CPU
     ↓
P1 → P2 → P3 → P1 → P4 → ...
```

This is **CPU virtualization**.

The lecture calls the ability for multiple programs to appear to run at the same time one of the important illusions created by an OS.

---

# 22. Concurrency vs Parallelism — Important Clarification

For the single-CPU scenario shown here:

```text
A → B → C → A → B → C
```

the programs make progress during overlapping periods but aren't literally executing simultaneously on that one CPU.

Think:

```text
Concurrency
= dealing with multiple progressing tasks

Parallelism
= literally executing multiple tasks at the same instant
```

With multiple CPU cores, true parallel execution can also occur.

For this lecture, focus on the single-CPU illusion:

```text
fast interleaving → apparent simultaneous execution
```

### Must-remember statements

**Program Counter (PC):**

> Holds the address of the next instruction to execute.

**CPU cycle:**

> Fetch → Decode → Execute → repeat.

**OS:**

> Manages hardware/resources and provides useful abstractions/services to programs.

**CPU Scheduling:**

> Determines which process gets the CPU.

**CPU Virtualization:**

> OS creates the illusion that multiple programs have access to the CPU by multiplexing/interleaving CPU execution.

**Context Switch:**

> CPU execution changes from one process to another while preserving enough execution state to resume later.

**Why OS?**

```text
CPU management
Memory management
Device/I/O management
Storage/file management
Protection
Convenient abstractions
```

And the most important mental model from this whole lecture is:

> **The CPU doesn't understand “apps.” It fetches and executes instructions. The OS is software whose instructions also run on that CPU, and it orchestrates the machine so many programs can safely and conveniently use the hardware.**

That's the foundation the rest of OS sits on.
