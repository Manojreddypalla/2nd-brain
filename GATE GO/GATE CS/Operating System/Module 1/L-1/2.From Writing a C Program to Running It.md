# From Writing a C Program to Running It — Full Notes

These notes follow the material you provided: **preprocessor → compiler → assembler → linker → loader**, along with logical addresses and the role of memory.

---

## 1. Big Picture

When we write a C program, the CPU **cannot directly execute the C source code**.

For example:

```c
#include <stdio.h>

int main() {
    printf("Hello");
    return 0;
}
```

The program goes through several stages before it can actually execute:

```text
Source Program
   hello.c
      ↓
 Preprocessor
      ↓
   hello.i
      ↓
   Compiler
      ↓
   hello.s
      ↓
  Assembler
      ↓
   hello.o
      ↓
    Linker
      ↓
 Executable
   a.out
      ↓
    Loader
      ↓
 Main Memory
      ↓
     CPU
```

The important stages are:

**Preprocessor → Compiler → Assembler → Linker → Loader**

---

# 2. Preprocessor

The **preprocessor processes preprocessor directives**, generally the lines beginning with `#`, before actual compilation.

Example:

```c
#include <stdio.h>
```

The source starts as:

```text
hello.c
```

After preprocessing:

```text
hello.i
```

### Main idea

For an `#include`, the required header content is incorporated into the preprocessed source.

Mental model:

```text
hello.c

#include <stdio.h>
int main() {...}

        ↓ Preprocessor

hello.i

[required header declarations/code]
int main() {...}
```

So `hello.i` is still essentially **C source code**, but preprocessing has already been performed.

---

# 3. Compiler

Now:

```text
hello.i
   ↓
Compiler
   ↓
hello.s
```

The **compiler converts the preprocessed C program into assembly language**.

For example, conceptually:

```c
int a = 5;
```

could eventually correspond to assembly-like instructions involving registers and memory.

Example:

```asm
mov ...
```

The important point is:

> **Compiler: High-level language → Assembly language**

This is one of the more complex stages because the compiler has to understand things such as expressions, types, control flow, variables and generate suitable machine-level operations.

---

# 4. An Important Problem: Where Will the Program Be Loaded?

This leads to an important OS concept.

Suppose we compile:

```text
hello.c
```

today.

But we execute it:

```text
5 minutes later
```

or even much later.

During compilation, the compiler cannot know exactly **where the program will physically reside in RAM when it eventually executes**.

Imagine RAM:

```text
Physical Memory

┌────────────────────┐
│ Operating System   │
├────────────────────┤
│ Chrome             │
├────────────────────┤
│ VS Code            │
├────────────────────┤
│ Free               │
├────────────────────┤
│ Other Process      │
└────────────────────┘
```

Where should `hello` go?

The compiler cannot predict the future state of physical memory.

This motivates the idea of **logical/virtual addressing**.

---

# 5. Logical Address

Instead of designing the program around its eventual physical RAM location, the program works using a **logical address space**.

Conceptually, each process can think:

```text
"My address space"

0
│
│ Program
│ Data
│ Heap
│ ...
│ Stack
│
Maximum Address
```

Meanwhile, actual physical memory contains many things:

```text
Physical RAM

┌──────────────┐
│ OS           │
├──────────────┤
│ Process A    │
├──────────────┤
│ Process B    │
├──────────────┤
│ Process C    │
└──────────────┘
```

Therefore:

```text
Program
   ↓
Logical / Virtual Address
   ↓
Address Translation
   ↓
Physical Address
   ↓
RAM
```

### Key idea

The compiler does **not need to know the final physical location of the program in RAM**.

The required address translation is handled later by the system.

This concept becomes extremely important when studying:

- Memory management
    
- Paging
    
- Segmentation
    
- Virtual memory
    
- Page tables
    

---

# 6. Why Logical Addresses Are Useful

Suppose two programs both internally use an address such as:

```text
0x1000
```

That does **not necessarily mean they access the same physical RAM location**.

Conceptually:

```text
Process A

Logical 0x1000
      ↓
Physical 0xA500
```

while:

```text
Process B

Logical 0x1000
      ↓
Physical 0xF200
```

This allows processes to have their own address spaces.

That gives us an important abstraction:

> **Each process behaves as though it has its own memory space.**

---

# 7. Assembler

After compilation:

```text
hello.s
   ↓
Assembler
   ↓
hello.o
```

The assembler converts **assembly instructions into machine-code/object representation**.

For example, conceptually:

```asm
mov ...
```

becomes binary-encoded machine instructions.

So:

> **Assembler: Assembly language → Object/Machine code**

The output is commonly an:

```text
Object file (.o)
```

Example:

```text
hello.o
```

### Important

The object file is **not necessarily the final executable**.

It may still contain references that must be resolved by the linker.

---

# 8. Linker

Suppose the program consists of multiple source files:

```text
a.c
b.c
```

They can be compiled separately:

```text
a.c
 ↓
a.o

b.c
 ↓
b.o
```

Then:

```text
a.o ─┐
     ├──→ Linker → Executable
b.o ─┘
```

The **linker combines object files and resolves references between them**.

---

# 9. Why Do We Need Linking?

Consider:

### `a.c`

```c
int sum(int, int);

int main() {
    int x = sum(2, 3);
}
```

### `b.c`

```c
int sum(int a, int b) {
    return a + b;
}
```

When `a.c` is compiled, the compiler knows:

```text
sum() exists and has this interface.
```

But its implementation is in another file.

After separate compilation:

```text
a.c → a.o
b.c → b.o
```

the linker connects them:

```text
a.o ─────┐
         ↓
       Linker
         ↓
       a.out
         ↑
b.o ─────┘
```

So:

> **The linker resolves references between separately compiled object files/libraries and creates the executable.**

---

# 10. Function Declaration vs Definition

This distinction helps understand linking.

### Declaration / Prototype

```c
int sum(int, int);
```

It tells the compiler:

> A function called `sum` exists and has this type.

### Definition

```c
int sum(int a, int b) {
    return a + b;
}
```

It contains the actual implementation.

Therefore, the declaration can appear in one compilation unit while the implementation comes from another object file or library and is connected during linking.

---

# 11. Header Files and Linking

Consider:

```c
#include <stdio.h>
```

For a function such as:

```c
printf()
```

the header provides the necessary **declaration/interface information** for compilation.

The actual compiled implementation of library functions is provided separately through libraries and connected as part of the linking/loading mechanism.

This distinction is important:

```text
Header
   ↓
"What does this function look like?"

Library implementation
   ↓
"Here is the actual compiled function."
```

---

# 12. Loader

Once linking is complete, we have an executable:

```text
a.out
```

But having an executable stored on disk does **not mean it is currently executing**.

For execution:

```text
Executable
    ↓
  Loader
    ↓
Process address space prepared
    ↓
Ready to execute
```

The **loader is responsible for loading/preparing the executable for execution in memory**.

This is where Operating System involvement becomes especially important.

---

# 13. Program vs Process

This distinction is worth locking in now.

### Program

A program is a **passive executable stored on disk**.

Example:

```text
a.out
```

### Process

When that program is loaded and executing, it becomes a **process**.

```text
Program on Disk
      ↓
    Loader
      ↓
Process in execution
```

So:

> **Program = passive file**  
> **Process = program in execution**

# 15. What Each Stage Does

|Stage|Input|Output|Main Job|
|---|---|---|---|
|Preprocessor|`.c`|`.i`|Handles preprocessing directives|
|Compiler|`.i`|`.s`|Converts C → Assembly|
|Assembler|`.s`|`.o`|Converts Assembly → Object code|
|Linker|`.o` files/libraries|Executable|Combines modules and resolves references|
|Loader|Executable|Running process|Prepares program for execution|

---

# 16. GATE Important Points

### Point 1

**Assembler does NOT normally produce the final executable.**

```text
Assembler → Object file
Linker → Executable
```

### Point 2

External references between modules are primarily resolved by the:

**Linker**

### Point 3

Operator precedence and language semantics are handled during:

**Compilation**

### Point 4

Putting/preparing the executable in memory for execution is the job of:

**Loader**

### Point 5

The compiler doesn't need to know the program's eventual physical RAM location.

The system uses logical/virtual addressing and later maps it to physical memory.

# 17. Quick Memory Trick

Remember:

```text
C → A → B → E → M
```

Meaning:

```text
C source
   ↓ Compiler
Assembly
   ↓ Assembler
Binary/Object
   ↓ Linker
Executable
   ↓ Loader
Memory
```

Or the full version:

```text
.c
 ↓ Preprocessor
.i
 ↓ Compiler
.s
 ↓ Assembler
.o
 ↓ Linker
Executable
 ↓ Loader
Memory
```

### One-line summary

> **Preprocessor prepares the source, compiler generates assembly, assembler generates object code, linker creates the executable, and loader prepares it in memory for execution.**
