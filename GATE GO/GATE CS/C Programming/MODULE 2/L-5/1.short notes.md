# C Programming — Lecture 5

## Functions + Writing C → Running C

# 1. Functions

### Why functions?

Large programs are difficult to manage.

```text
Large Program
     ↓
Smaller logical units
     ↓
Functions
```

Functions provide **modularity** and make programs easier to manage/read.

Mathematical analogy:

```text
y = f(x)

x → input
f → operation
y → output
```

---

# 2. Function Syntax

```c
return_type function_name(parameter_list)
{
    // statements

    return value;
}
```

Example:

```c
int square(int x)
{
    return x * x;
}
```

### Parts

```text
int       → return type
square    → function name
int       → parameter type
x         → parameter name
{ }       → function body
```

Curly braces group statements into a block.

---

# 3. Function Definition

General:

```c
type fname(type arg1, type arg2)
{
    // local variables
    // executable code
}
```

Example:

```c
float mul(float x, float y)
{
    float result;

    result = x * y;

    return result;
}
```

- `result` → local variable
    
- `x, y` → parameters
    
- `return result` → returned value.
    

---

# 4. Function Call

```c
fname(arg1, arg2);
```

Example:

```c
int y;

y = mul(10, 5);
```

Flow:

```text
main()
  ↓
mul(10,5)
  ↓
function executes
  ↓
returns result
  ↓
stored in y
```

# 5. Function Declaration / Prototype

Declaration = **Function Prototype**

```c
int mul(int m, int n);
```

It tells the compiler:

```text
Function name
Parameter types
Return type
```

No function body is present.

---

## Parameter Names Are Optional in Prototype

Both are valid:

```c
int mul(int a, int b);
int mul(int, int);
```

Only parameter **types** are important in the prototype.

# 6. Declaration + Definition

```c
int fun(int x, int y);   // declaration

int main()
{
    int a;
    a = fun(2,3);
}

int fun(int x, int y)    // definition
{
    return x+y;
}
```

```text
Declaration
    ↓
Compiler knows function interface

Definition
    ↓
Actual implementation
```

# 7. Function Declaration Before Call

If a function is called before its definition, a declaration/prototype should be available first.

```c
int fun(int x, int y);

{
    int a;
    a = fun(2,3);
}

{
    return x+y;
}
```

# 8. `void` Functions

```c
void display(void)
{
    printf("No type, no parameters");
}
```

```text
void before function
→ no return value

void inside ()
→ no parameters
```

A `void` function can omit `return`.

It may also use:

```c
return;
```

to terminate execution early.

# 9. Pass-by-Value

### C uses pass-by-value.

```text
Actual argument
      ↓
     COPY
      ↓
Formal parameter
```

Example:

```c
swap(a,b);
```

If:

```text
a = 3
b = 4
```

then inside:

```text
x = 3
y = 4
```

`x` and `y` are separate variables.

Therefore changing `x,y` **doesn't change** `a,b`.

---

# 10. Swap Example

```c
void swap(int x, int y)
{
    int temp = x;

    x = y;
    y = temp;
}
```

Call:

```c
int a = 3;
int b = 4;

swap(a,b);
```

Inside:

```text
x = 3
y = 4

temp = 3
x = 4
y = 3
```

But in `main`:

```text
a = 3
b = 4
```

### Result

❌ Original variables are **not swapped**.

Why?

```text
a ──copy──→ x
b ──copy──→ y
```

---

# 11. Activation Record (AR)

A function invocation creates an **Activation Record (AR)**.

It contains the execution information/state associated with that function call.

Example:

```text
Stack

┌─────────────┐
│ func AR     │ ← current function
├─────────────┤
│ main AR     │
└─────────────┘
```

So `main` and `swap` have **separate activation records**.

# 12. GATE 2019 — Function Tracing

Given:

```c
int jumble(int x, int y)
{
    x = 2*x + y;
    return x;
}

int main()
{
    int x = 2, y = 5;

    y = jumble(x,y);
    x = jumble(x,y);

    printf("%d %d",x,y);
}
```

### First call

```text
jumble(2,5)

x = 2(2)+5
  = 9

y = 9
```

State:

```text
x = 2
y = 9
```

### Second call

```text
jumble(2,9)

x = 2(2)+9
  = 13
```

Final:

```text
x = 13
y = 9
```

Output:

```text
13 9
```

Key: **track copies inside each function call separately.**

# 15. Preprocessor

```text
.c → .i
```

Example:

```c
#include <stdio.h>
```

The preprocessor handles preprocessing directives such as `#include`.

Output:

```text

```

# 16. Compiler

```text
.i → .s
```

Converts:

```text
C source → Assembly
```

Example conceptual instruction:

```asm
mov R1, 1000
```

The compiler is the **most computationally complex stage among CALL**, according to the lecture.

---

# 17. Assembler

```text
.s → .o
```

Converts:

```text
Assembly → Object code
```

Output:

```text
hello.o
```

⚠️ **Assembler does NOT create executable.**

---

# 18. Linker

```text
.o + libraries/object files
        ↓
    Executable
```

Responsibilities:

- Combines object files.
    
- Resolves **external labels/references**.
    
- Creates executable.
    

```text
a.o ──┐
      ├──→ Linker → executable
b.o ──┘
```

---

# 19. Loader

```text
Executable
     ↓
   Loader
     ↓
Memory
```

The loader places the executable in memory **in preparation for execution**.

```text
Executable on disk
        ↓
      Loader
        ↓
Program in memory
        ↓
Ready to run
```

# 21. Logical Address

The compiler generates **logical addresses**.

Example:

```asm
MOV R1, 1000
```

`1000` is treated as a logical/relocatable address.

### Why?

The compiler cannot know the exact physical RAM location where the program will execute later.

```text
Compile
   ↓
years pass
   ↓
Run
```

The physical memory arrangement can be different.

---

# 22. Logical vs Physical Address

```text
Compiler
   ↓
Logical Address
   ↓
OS / address translation
   ↓
Physical Address
```

```text
Logical Address ≠ Physical Address
```

The OS translates the logical address based on where the program is loaded in physical memory.

|Action|Stage|
|---|---|
|`.c → .i`|**Preprocessor**|
|`.i → .s`|**Compiler**|
|`.s → .o`|**Assembler**|
|`.o → executable`|**Linker**|
|Executable → memory|**Loader**|
|Operator precedence|**Compiler**|
|External labels resolved|**Linker**|
|Static data placed in memory|**Loader**|
|Highest complexity among CALL|**Compiler**|

# 24. Separate Compilation

Multiple `.c` files can be compiled independently.

```text
a.c → a.i → a.s → a.o
b.c → b.i → b.s → b.o
```

Then:

```text
a.o
b.o
 ↓
Linker
 ↓
Executable
```

This allows different source files to be **compiled separately**.

# 25. Two-File Example

### `a.c`

```c
#include <stdio.h>

int sum(int x, int y);

int main()
{
    int a;

    a = sum(2,3);

    printf("%d", a);
}
```

### `b.c`

```c
int sum(int x, int y)
{
    return x+y;
}
```

Here:

```text
a.c
 ↓
calls sum()

b.c
 ↓
defines sum()
```

After compilation:

```text
a.o → reference to sum
b.o → definition of sum
```

Linker connects them.

# 28. Stack & Activation Record

When:

```c
main()
{
    func(5);
}
```

calls `func()`:

```text
Stack

┌──────────────┐
│   func AR    │
├──────────────┤
│   main AR    │
└──────────────┘
```

The **function's activation record is placed on the stack**.

---

# 29. RBP — Base Pointer

```text
RBP = Base Pointer
```

It provides a stable reference point for the **current function's stack frame**.

```text
RBP
 ↓
┌──────────────┐
│ current AR   │
└──────────────┘
```

---

# 30. RSP — Stack Pointer

```text
RSP = Stack Pointer
```

Points to the current stack position/top.

```text
RSP
 ↓
Stack
```

During function execution, `RSP` changes as stack space is allocated/deallocated.

---

# 31. Function Prologue

Typical beginning:

```asm
push rbp
mov  rbp, rsp
```

Conceptually:

```text
Save old frame information
        ↓
Establish current frame
```

This creates the function's stack-frame structure.

---

# 32. Local Variables

Example:

```c
void func(int arg)
{
    int a = 5;
    g = 5;
}
```

`a` is local to `func()` and is represented within its stack frame.

Conceptually:

```text
RBP → ┌────────────┐
      │ saved RBP  │
      ├────────────┤
      │ arg        │
      ├────────────┤
      │ a = 5      │
      └────────────┘
           ↑
          RSP
```

The lecture's assembly accesses these through offsets relative to `RBP`.

---

# 33. Function Argument

For:

```c
func(5);
```

the example places `5` in:

```text
EDI
```

before:

```asm
call func
```

Conceptually:

```text
5
↓
EDI
↓
func()
```

---

# 34. `call`

```asm
call func
```

Transfers execution:

```text
main()
   ↓
func()
```

and creates the function's execution context/activation record.

---

# 35. `ret`

```asm
ret
```

returns execution:

```text
func()
   ↓
main()
```

The function's stack-frame state is restored/removed as part of the return sequence.

---

# 36. Function Epilogue

Typical ending:

```asm
pop rbp
ret
```

Conceptually:

```text
Restore previous frame
        ↓
Return to caller
```
