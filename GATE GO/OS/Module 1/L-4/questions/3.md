### User-Level vs Kernel-Level Threads — GATE Short Notes

|Option|Statement|Why?|
|---|---|---|
|**1**|Context switch time is longer for **kernel-level threads**|✅ **TRUE** — Kernel must be involved → mode switch/scheduler overhead. User-level thread switching can happen entirely in user space.|
|**2**|User-level threads need **no hardware support**|✅ **TRUE** — Managed by a user-level thread library; kernel doesn't need to know about individual threads.|
|**3**|Related kernel-level threads can run on **different processors**|✅ **TRUE** — Kernel sees each thread independently and can schedule them on different CPUs/cores simultaneously.|
|**4**|Blocking one kernel-level thread blocks **all related threads**|❌ **FALSE** — This is a property of **user-level threads**. If one ULT makes a blocking system call, the **whole process may block**.|

### 🔥 The pattern to remember

**User-Level Threads (ULT)**

- Kernel **doesn't know** individual threads.
- ⚡ Thread switch → **fast**
- ❌ One blocking system call → **entire process may block**
- ❌ Usually cannot exploit multiple processors simultaneously.
- No special kernel/hardware support required.

**Kernel-Level Threads (KLT)**

- Kernel **knows and schedules** each thread.
- 🐢 Switch → relatively **slower**
- ✅ One thread blocks → **other threads can continue**
- ✅ Different threads can run on **different CPUs**.

### GATE Trap ⚠️

Don't confuse:

> **"Thread has its own stack"**  
> with  
> **"Thread's stack is inaccessible to other threads."**

A thread **owns its own stack**, but because threads of the same process share the **same address space**, another thread can technically access that stack if it has the appropriate address/pointer.

**Ownership ≠ accessibility.** This distinction is very GATE-worthy.
